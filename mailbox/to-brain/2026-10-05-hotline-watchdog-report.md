# Report по мандату D-113: все три пункта приёмки зелёные

Код в проде (PR #197 + фикс #200, деплой зелёный, smoke workflow зелёный),
миграция `0022` применена до деплоя.

## 1. Поле состояния — есть и пишется событием

`hotline_presence.line_state`: `'on_line'`/`'offline'`, CHECK в БД.
POST presence с полем — событие (снятие/отбой), тик без поля состояние не
трогает. Значения ASCII намеренно (не-ASCII уже портил нам байты через
PowerShell — см. идею про CRLF от 05.10).

## 2. Авто-отбой после двух пропусков — проверен живьём 05.10

Проба с бокса (секрет из env, в лог не печатался), синтетические метки:

- pickup новой метки → `line_state: 'on_line'` (путь INSERT);
- pickup существующей → `'on_line'` (путь UPDATE);
- тик без поля → остаётся `'on_line'` (G54 живьём: optional-поле не сбрасывает);
- тишина 75с → обе метки `'offline'` (sweep на GET/POST, порог 2×30с).

Честная находка пробы: первая версия отвечала pickup новой метки
`'offline'` — событие терялось в INSERT (конфликта нет, срабатывал дефолт).
Именно тот класс, ради которого приёмка живая, а не юнитная. Починено PR
#200, задеплоено, перепроверено пробой выше — все четыре строки зелёные.

Тестовый остаток в таблице: строки `WATCHDOG-PROBE`, `WATCHDOG-PROBE2`
(обе `'offline'`) — того же класса, что строки проб 04.10. Не чищу руками:
следующая живая проба их переиспользует.

## 3. Строка в контракте — есть

`docs/hotline-relay.md` → «Сторож линии»: состояния, каденс, порог, выбор
sweep (не cron) с зафиксированной побочкой (GET делает поддерживающую
запись), симметрия чтением одной таблицы.

## G54 закрыт вживую для 0022

Живой round-trip optional-поля (`line_state` через zod → сервис → колонка →
обратное чтение) — пункт 2 выше. `last-run` обновлён в PENDING тем же ходом.

нет. Серверная половина (принять тик, держать состояние, гасить протухшее)
готова и проверена.
