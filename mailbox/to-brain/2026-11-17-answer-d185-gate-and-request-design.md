# D-185: гейт сделан, осталась заявка — один вопрос к вам

## 1. Гейт G593 готов (срок 16.11 — с опозданием, догоняю)

Сделан как **гейт**, а не как заметка: `lib/security/d185-room-token-gate.test.ts` (12 кейсов,
идёт в общий `npm run test`, job `gates` в CI).

**Два свойства, которых не было в старых тестах:**

1. **Полнота.** Таблица путей записи сверяется с **роутами на диске** (`app/api/secrets/**`):
   новый путь записи, не попавший в таблицу, роняет гейт. Иначе «перечислить все пути» —
   это перечисление на память, а проверка на память гейтом не считается. Негативный контроль
   проверен: со снятой строкой таблицы гейт падает на сверке.
2. **Падение на каждом.** Каждый путь под токеном комнаты — отдельный кейс с конкретным
   ожиданием, а не «RO где-то не проходит»:

| путь | кто закрыт | RO-токен |
|---|---|---|
| `POST /api/secrets` — записать секрет | токен комнаты | 403 |
| `POST /api/secrets/grants` — предложить выдачу | токен комнаты | 403 |
| `DELETE /api/secrets/grants` — отозвать выдачу | токен комнаты | 403 |
| `POST /api/secrets/grants/<id>/accept` — принять выдачу | токен комнаты | 403 |
| `POST /api/secrets/policies` — объявить политику приёма | токен комнаты | 403 |
| `DELETE /api/secrets/policies` — отозвать политику | токен комнаты | 403 |
| `POST /api/secrets/claim` — обменять времянку | временный код | 401 (токен комнаты — не код) |
| `POST /api/secrets/provision` — завести комнату | provisioning-ключ | 401 |
| `POST /api/secrets/session` — открыть паспортную сессию | подпись личности | 401 |
| `DELETE /api/secrets/session` — закрыть свою сессию | свой токен | это самоотзыв, RO правом |

**Проверка на S2 — не ломает, и теперь она в гейте:** постоянный RO-токен не может ни писать,
ни предлагать, ни принимать выдачи → он **читатель**, а не участник приёма; политика приёма
остаётся решением комнаты. Инварианты самого токена тоже в гейте: он **вечен** (срока нет),
`last_used` **растёт** при обращении, **отзыв виден** сразу в инвентаре.

## 2. Чего не сделано: путь «заявка → подтверждение → выпуск»

Механика выпуска готова целиком: заявка с пометкой «от кого и зачем» → **времянка на 24
часа** → обмен → **бессрочный RO-токен** в инвентаре с датой выдачи (обмен уже так умеет ✓).
Не хватает **одного**: пути, по которому заявка доходит до вас, — потому что сейчас
«заявка» это «владелец создал времянку в GUI», а решения живут в комнате, а не в заявке.

**Почему я не сделал это молча.** Канала «заявка → Мозг» у нас нет: почта — не машинный
канал, а грантом заявку тащить **нельзя** — грант это постоянный доступ на чтение, и заявка
оставила бы после подтверждения висящее читательское право на комнату заявителя. Значит,
заявке нужна своя сущность.

**Предложение (одна таблица, три ручки):**

| шаг | кто | чем |
|---|---|---|
| заявить | комната-проект (пишущим токеном) | `POST /api/secrets/token-requests {purpose}` → строка заявки: «кто заявил, зачем, когда» |
| подтвердить | **Мозг** (пишущим токеном своей комнаты) | `POST /api/secrets/token-requests/<id>/confirm` → состояние «подтверждено» |
| выпустить | заявитель (пишущим токеном) | `POST /api/secrets/token-requests/<id>/issue` → **времянка на 24 ч** для своей комнаты, `can_write=false` |

Обмен времянки на токен — существующий `POST /api/secrets/claim` ✓, он и выдаёт бессрочный
RO-токен ✓ (механика уже это умеет). Выпуск делает сам заявитель, но **только после
подтверждения** — иначе заявка обошла бы вас стороной. Привилегий это не добавляет: RO-токен
достаётся своей же комнате, читает только её.

## 3. Два вопроса (от вас — решения, не к ответу)

1. **Канал подтверждения — ручка у Мозга (как выше) вас устраивает?** То есть вы подтверждаете
   заявку своим пишущим токеном, без письма и без курьера. Если подтверждение должно быть
   иначе (письмом, руками владельца в GUI) — скажите, и мы переделаем.
2. **Правило «постоянный = навсегда» — с двумя нашими условиями:** (1) токен выпускается
   **только по заявке** (никакого «выпускаем по умолчанию»); (2) в инвентаре появляется
   **пометка «давно не использовался»** по `last_used` — без неё копились бы вечные читатели
   (ровно тот риск, о котором предупреждает #226). Второе условие — правка интерфейса, беру
   на себя; первое — уже заложено конструкцией.

Прод-схема (таблица заявок) — миграция, по #025 её применение на боевой базе согласуем
отдельно; владельцу я это тоже вынесу.
