# D-061: паспортный путь Сабантую открыт, ждём их прогон

## Что сделано

1. **Личность заведена.** `passport_identity` id 3: `identity_value = 1257598398`
   (`repository_id` для `Valstan/SabantuyMalmyzh`, неизменяемый), комната
   `sabantuymalmyzh` (`project_id 5`), **`can_write = true`** — зеркалированию нужна запись,
   ro-токен ответил бы `403` на `POST`, и снаружи это читалось бы как «паспорт не работает».
2. **Не доехавший токен отозван.** В комнате лежал rw-токен `skm_-FGLAD3g` от 29.06 без срока,
   **ни разу не использованный** (`last_used_at` пуст) — тот самый «токен потерялся при
   доставке». Отозван с записью в аудит комнаты. Его значение не знал никто: в БД только хеш,
   так что терять было нечего, а висячий бессрочный rw-доступ — чистый минус.
3. **Гайд.** В `docs/secrets-client-guide.md` добавлен явный порядок выбора пути (паспорт →
   времянка → break-glass → руки владельца) со ссылкой на D-061: онбординг проекта с рабочим
   GitHub Actions ручной выдачей теперь назван регрессом, а не «как обычно».
   В `docs/passport-server.md` — правило `can_write` по факту записи (в прежнем примере
   runbook'а было зашито `false`, и следующий пишущий проект наступил бы на те же грабли).

## Поправка к мандату: 409-гейт здесь не срабатывает

Пункт 1 предполагал возможный 409 и перевыпуск. В нашей архитектуре этого не случается:
409-гейт живёт в `/api/secrets/provision` (первый токен по общему ключу), а паспортный путь
туда не заходит вовсе. `POST /api/secrets/session` создаёт **новую** строку `secrets_token`
для комнаты по строке реестра — то есть паспорт с самого начала умел выдавать rw-токен
комнаты, и «чего не хватает» из пункта 2 отвечать не пришлось. Не хватало ровно одной строки
реестра, а её заведение — операция владельца по конструкции ADR-0012 (§«Комнату паспорт не
заводит»): это регистрация личности, а не передача значения. Ключи ходят без рук владельца —
инвариант D-061 соблюдён.

Единственная настоящая шероховатость: реестр личностей ведётся SQL-runbook'ом, GUI-раздела
нет — это остаток вехи 2 волны 2, он у нас в отложенном и не блокирует Сабантуя.

## Ход Сабантуя — и что должно совпасть

Их воркфлоу забирает удостоверение и меняет на токен комнаты:

```bash
# permissions: id-token: write
ASSERTION="$(curl -sf -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=karman-vault" | jq -r .value)"
curl -sf -X POST "$VAULT_URL/api/secrets/session" -H "Authorization: Bearer $ASSERTION"
# → 201 {"ok":true,"token":"skm_…","expiresAt":"…","slug":"sabantuymalmyzh","canWrite":true}
```

Три условия, на которых обычно спотыкаются (все три у них сейчас сходятся):

- `audience=karman-vault` — ровно эта строка, иначе `401` без объяснения причины;
- прогон с **`refs/heads/main` или `master`**: субъект пинуется
  `^repo:[^:/]+/[^:/]+:ref:refs/heads/(main|master)$`, то есть из PR-прогона или с тега
  сессия не откроется. У них дефолтная ветка `main` — подходит;
- токен сессии **со сроком** (TTL 60 мин): его берут в каждом прогоне заново, а не кладут
  в `SECRETS_TOKEN` навсегда. Самоотзыв в конце — `DELETE /api/secrets/session`.

## Приёмка: чего ещё нет

Твоя формулировка приёмки — их первый успешный `POST` секрета в нашем аудите. **Этого пока
нет**: наша половина работы закончена, их прогон — их ход. Подтвердим строкой аудита комнаты 5

```sql
select at, action, detail, actor from secrets_audit
 where project_id = 5 order by id desc limit 10;
```

— ждём пару `session_open` (actor `passport:Valstan/SabantuyMalmyzh`) → `push`. Отпишу, как
появится; если у них `403` на записи или `401` на сессии — причина будет видна в том же
аудите, и это к нам, а не к ним.
