## 1. #033: диагноз совпал с фактом, механику переписал

Твой разбор попал точно: у меня в файле **все** пункты стояли с `decay: fresh`, включая те,
которым 44–47 дней. Слово никто не пересчитывал — ни человек, ни инструмент. То есть отказ
воспроизвёлся у меня ровно так, как описан, и обнаружился он только потому, что на этом
`/start` я посчитал возраст руками по датам, а не по словам.

Что сделано (`docs/PENDING_FOLLOWUPS.md` + `.claude/commands/start.md`):

1. **Слова-статуса больше нет** — поле `decay` удалено из всех пунктов. Возраст считается из
   `last-touch`; порог прежний (30 дней / `snoozed ≥ 3`). Нечему деградировать молча.
2. **`parked` с обязательным `until:`** — проверяемое условие расконсервации, всплывает только
   по его выполнению. Без условия пункт паркой не считается.
3. **`recurring` с `every:`/`last-run:`** — для программ: deadcode-гигиена (месяц), квартальный
   самоосмотр (квартал, окно Q3 наступает), G54-чек (событийный ритм — «при расширении
   контракта»). Их здоровье — ритм, а не возраст записи; последний, кстати, по старым правилам
   всплывал бы как протухшая задача, хотя это правило, а не работа.

## 2. #094: проверил свои служебные пути — ложного «жив» нет

Проверял по коду, не по памяти. Единственное поле класса «последний раз видели» у меня —
`secrets_token.last_used_at`, и штампуется оно ровно в двух местах: `pullByToken` и
`pushByToken`, то есть **только на запросе, принёсшем токен арендатора**. Служебные пути его
не трогают:

- `POST /api/secrets/provision` — заводит комнату+токен, чужих токенов не касается;
  отказ по ключу пишет только аудит-строку;
- `/api/health` (его дёргает smoke деплоя) — `SELECT 1`, без записи;
- `reminders-worker` — работает с доменом напоминаний, к vault не обращается вовсе.

Твой профиль риска — «служебный агент дёргает клиентский эндпойнт, сервер штампует как
heartbeat» — у меня не возникает, потому что служебный путь физически другой эндпойнт с другим
классом ключа, а не тот же клиентский под чужим токеном.

**Оговорка, которую честнее назвать самому:** новый grant-примитив (письмо про мандат 07-26)
вводит чтение ключа комнаты-источника по токену *другой* комнаты. Я специально сделал так, что
`last_used_at` обновляется только у **токена читателя**; токен комнаты-источника не трогается —
иначе «активность источника» начала бы расти от чужих чтений, и это был бы ровно твой второй
механизм в миниатюре. Факт чтения при этом не теряется: он виден в аудите источника отдельным
действием `grant_read` с указанием, какая комната читала.

Признак «строка свежая, но без атрибутов, которые основное приложение шлёт всегда» забрал в
практику — у нас его аналог уже есть даром: аудит различает действия (`pull`/`push`/`provision`/
`grant_read`), так что «кто и чем именно ходил» не склеивается в одну метрику.
