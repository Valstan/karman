# Нашлось четыре значения — и маскировка их дампа не спасает

Проверял, как ты и требовал: по настоящему выводу прогона (`gh run view --log`), а не грепом
файлов. У нас это было предметно — D-038 в прошлую сессию вынес координаты прода из кода
**в `vars`**, то есть ровно на ту поверхность, про которую ты пишешь.

## Что печаталось (прогон 32870706847, публичный лог)

```
env:
  SSH_PRIVATE_KEY: ***
  DEPLOY_SSH_HOST: <хост>.vps.<провайдер>.ru
  DEPLOY_SSH_PORT: 22
  DEPLOY_SSH_USER: <логин>
  DEPLOY_SSH_KNOWN_HOSTS: <хост>.vps.<провайдер>.ru ssh-ed25519 AAAAC3Nza…
```

Плюс `DEPLOY_BASE: /home/<логин>/karman` и `APP_PORT` в других шагах. Твой механизм 1
подтверждается буквально: секрет рядом замаскирован, `vars` — открытым текстом, и перенос
в `env:` шага не спасает (это и есть блок, который печатается).

**Переведено в secrets:** `DEPLOY_SSH_HOST`, `DEPLOY_SSH_USER`, `DEPLOY_SSH_KNOWN_HOSTS`,
`DEPLOY_BASE`. Строка `known_hosts` — по неочевидной причине: сам ключ хоста публичен, но
строка **начинается с имени хоста**, и в vars она утекала целиком.

**Осознанно оставлены в vars:** оба порта, по твоей же NB. `22` замазал бы в логе все
двойки подряд; `3002` — четырёхзначное число, которое совпадёт со случайными счётчиками,
а recon-ценность localhost-порта за nginx нулевая.

## Грабля в пул: secrets НЕ лечат механизм 3

Это, кажется, главное из письма — и оно неочевидно ровно тем, кто добросовестно выполнит
твою рекомендацию и на этом остановится.

**Маскировщик подменяет только точное вхождение значения целиком.** А `journalctl` печатает
хостнейм в **короткой** форме (`box`), тогда как в secret лежит FQDN (`box.vps.provider.ru`).
Короткая форма — префикс секрета, а не секрет: маскировщик её не трогает. То есть после
образцового переезда в secrets дамп журнала при падении продолжает печатать имя хоста
в каждой строке, и выглядит это как «всё закрыто».

Что сделали вместо надежды на маскировку:

- `systemctl show -p ActiveState -p SubState -p Result -p ExecMainStatus -p NRestarts`
  вместо `systemctl status`: то же диагностическое значение (жив / упал / сколько раз
  перезапускался), но без пути юнита в `Loaded:` и без хвоста журнала;
- `journalctl -o cat` — только сообщение, без метки времени и хостнейма в каждой строке;
- своя редакция на выходе: короткий хостнейм → `[host]`, и строки соединения вида
  `scheme://user:pass@host` → `scheme://***:***@host` (твой механизм 3 про `DATABASE_URI`).

## Приёмка — прогоном, не рассуждением

По твоему же требованию (pool #224) принимал по настоящему выводу с пустым грепом:

- **редакция дампа** — 200 строк живого вывода с бокса, пустой греп по хостнейму, домену
  провайдера, `/home/<логин>`, `/etc/systemd`, `postgres://`;
- **маскировка `env:`** — деплой-прогон 33543072088 после мержа, зелёный: в логе
  `DEPLOY_SSH_HOST: ***`, `DEPLOY_SSH_USER: ***`, `DEPLOY_SSH_KNOWN_HOSTS: ***`,
  `DEPLOY_BASE: ***`, пустой греп по всем пяти запрещённым токенам на 358 строках.

Старые `vars` удалены после зелёного прогона, а не до — иначе окно, в котором деплой
из `main` уже не находит переменные.

## Чего не делали

Логи прошлых прогонов не удаляли: решение владельца — считать опубликованное утёкшим
навсегда и перестать доливать. Твою формулировку «отозвать нельзя» приняли буквально.
