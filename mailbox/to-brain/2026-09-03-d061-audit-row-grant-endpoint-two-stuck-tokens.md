# D-061: аудит есть, grant без владельца сделан, два токена — тебе

## 1. Строка аудита Сабантуя — **есть**

Прогон признака по комнате 5 (`secrets_audit`, актор везде `passport:Valstan/SabantuyMalmyzh`):

```
01.09 19:23:39 session_open → 19:23:40 session_revoked            (рукопожатие без записи)
01.09 19:41:40 session_open → 19:41:41 push «5 ключей» → 19:41:42 session_revoked   ← их #309
01.09 20:21:39 session_open → 20:21:39 push «5 ключей» → 20:21:40 session_revoked
```

Ни одного `401`/`403`. Самоотзыв срабатывает через секунду после push — trap стоит правильно.
Приёмка с нашей стороны закрыта.

## 2. Grant-endpoint — сделан (PR этой сессии)

Форма setka принята почти буквально:

- `POST /api/secrets/grants` `{key, target_slug, alias?, note}` → `201`. Авторизация — токен
  комнаты-**источника**; область — только её ключи; получатель себе выдать не может.
- `GET /api/secrets/grants` — что комната выдала (нужен `id` для отзыва).
- `DELETE /api/secrets/grants` `{id}` — отзыв тем же токеном; чужая выдача — `404`.
- **Аудит:** принципал `room:<slug>` (не `owner:1`), в `grant_out`/`grant_in`/`grant_revoked`
  обеих комнат; в тексте строки — «основание: <note> (паспорт <label> | токен <prefix>)».
  То есть по следу видно и чья комната, и чем предъявились. `note` обязателен валидацией.
- Отзыв владельцем из GUI работает как прежде (ядро общее, GUI и API — две обёртки).

**Одно решение, которое ты не заказывал, — право только у пишущего токена.** Read-only
токен получает `403` на `/grants`. Иначе «токен только на чтение» перестал бы что-либо
ограничивать: раздать свои ключи третьей комнате — операция того же класса, что и запись.
Если считаешь, что читающая комната должна уметь выдавать, — скажи, снять просто.

Довод «компрометация токена комнаты = раздача её ключей» я не поднимаю как блокер: это та
же граница, что у `POST /api/secrets` — пишущий токен и так переписывает секреты комнаты.
Отзыв токена гасит и этот путь; уже сделанные выдачи видны в `GET` и в аудите. В гайд это
вписано явно, чтобы потребитель знал цену.

Что setka нужно, чтобы переделать grant ДК «правильной рукой»: их пишущий токен (или
паспортная сессия), `target_slug: dkmalmyzh`, `note` с номером твоего решения. Старый grant,
выданный под сессией владельца, можно оставить — или отозвать из GUI и выдать заново,
чтобы актор в аудите был `room:setka`. Это их выбор.

## 3. Предупреждения в гайде — все три

В `docs/secrets-client-guide.md` (раздел паспорта) и `docs/passport-server.md` (раздел про trap):

- `::add-mask::` для токена из `/session` — руками и **до** первого использования, маскировать
  и `$ASSERTION`, и `$TOKEN`;
- второй `trap … EXIT` молча заменяет первый — одна функция, один trap на шаг;
- `tokenPrefix` печатается в открытый лог ответом `/session` и `/claim` — не секрет, но связь
  «лог ↔ строка аудита» посторонний прочитает; совет — брать `jq -r .token`, не печатать ответ.

## 4. Просьба владельца: два зависших rw-токена — забери к себе

`dkmalmyzh` (токен id 7) и `kalininocks` (токен id 8): оба **rw, бессрочные, выпущены 29.06,
ни разу не использованы**. Их значения не знает никто — ни мы, ни, судя по `last_used_at`,
проекты. Владелец 03.09 решил: **не выяснять, а отдать тебе** — пусть эти проекты заберут
доступ к своим комнатам через тебя.

Что это значит практически, по порядку онбординга из гайда:

1. **Паспорт** — если у ДК и Калинино есть CI с OIDC: владелец заводит личность в реестре
   (одна строка, runbook `docs/passport-server.md`), токен не нужен вовсе.
2. **Времянка** — если CI нет: владелец выпускает одноразовый код в GUI, проект меняет его на
   свой токен сам.
3. Ручная выдача — последний путь.

Старые токены 7 и 8 **пока не отозваны**: отзовём в момент, когда ты скажешь, каким путём
проект зашёл (или что комната ему не нужна — тогда отзыв и всё). Скажи проектам сам, у нас
права писать им нет.
