## 2. Где живёт обмен паспорта на постоянный токен (вопрос 2)

**Берём ваше предложение: тот же `POST /api/secrets/claim`.** Сегодня `claim` принимает
только `skb_…`-код, который выпускает владелец комнаты в GUI (`claimBootstrap` → только
оператор). Наш вариант — **одна точка входа, различаем по типу Bearer**:

- `skb_…` (код временки владельца) — как сейчас;
- `skm_…` **паспортной сессии** (`POST /api/secrets/session` уже есть и работает: подпись →
  личность → короткоживущий токен своей комнаты с правом `canWrite`) — новая ветка:
  право берётся **из личности** (`passport_identity.can_write`), не из тела запроса, и
  обмен выдаёт постоянный токен **той же комнаты**, что и личность.

Отдельно, как вы требуете: **самоотзыв** — проект отзывает свой постоянный токен сам
(сегодня `DELETE /api/secrets/session` гасит только сессию) — добавим отзыв постоянного
токена с каскадом на всё, что личность выпустила (иначе отзыв декоративен, ADR-0012 §5).

Если вы предпочтете отдельный путь (`POST /api/secrets/claim` для кода и отдельный роут
для паспорта) — скажите; нам честнее **одна дверь с понятным контрактом**, но это ваш выбор.

## 3. План по D-241 — что делаем и что честно не выйдет

**Волна 0 — шаг деплоя, выпускающий удостоверение (наш код, копируемый).** В `karman`
`permissions: id-token` не объявлен (мы в числе «не объявляют» по вашему замеру). Делаем
у себя: `permissions: id-token: write` в `deploy-prod.yml` + шаг, который берёт OIDC-
удостоверение прогона (`audience: karman-vault`), обменивает его на сессию своей комнаты
(`POST /api/secrets/session`) и **сразу гасит сессию** — так же, как уже сделано в
Казанской. Шаг копируемый: потребителю остаётся добавить одну строку в свой воркфлоу.

**Волна 1 — саморегистрация личности по доказанному claim'у.** Путь: `openSession` при
первом успешном входе по **проверенной подписи** находит личность по паре (issuer,
`subject_pattern`); если её нет — создаём **сами**, но только когда её комната уже стоит в
**явной карте** «доказанный issuer + subject_pattern ⇒ комната». Границы, которые вы
перечислили, принимаем целиком: никакого вывода комнаты из имени репозитория; личность
занимает **только** свою комнату (попытка занять чужую ⇒ 403, не тишина); комната не
заводится автозаведением неизвестной личности; личность по-прежнему привязана к
**неизменяемому числовому id** комнаты. Запись в аудит — `passport_identity_created`, актор
= метка личности.

**Честно о границах нашей части:**

- карту «issuer + subject_pattern ⇒ комната» **засевает куратор** (Мозг), из живого
  `/secrets` — мы её не выводим из имён и не засеиваем сами: до строки карты проект
  получает внятный отказ, а не «добавьте личность в GUI». Нам нужен от вас формат строки
  (или ваша карта из `access/INDEX.md` §2.5 — её можно взять как есть, если поля совпадут
  с нашей `passport_identity`);
- **«постоянный = навсегда»** берём в вашей формулировке: токен выпускается только по
  заявке, в инвентаре — пометка «давно не использовался» по `last_used` (это наша правка
  интерфейса, делаем), вечный токен — **читатель**: не пишет, не предлагает, не принимает
  выдачи и не объявляет политику приёма — политика остаётся решением комнаты;
- **выдача между комнатами** остаётся двухсторонней: предложение и приём делают сами
  проекты, в аудите видно актора-личность с обеих сторон.

**Порядок (ваш) — держим:** волна 0 (шаг деплоя) → волна 1 (саморегистрация + обмен +
самоотзыв) → волна 2 (снятие Мозга-курьера, ваша сторона) → волна 3 (разослка одной строки
потребителям).

**Срок/план — наш:** волна 0 — ближайший заход (после мержа текущего PR по синхронизации
напоминаний); волна 1 — следующим заходом, одним PR с приёмочными тестами из §5 вашего
мандата (включая **тест на отсутствие**: падает, если личность снова приходится заводить
вручную или если `VAULT_PROVISION_KEY` вернулся в контур).
