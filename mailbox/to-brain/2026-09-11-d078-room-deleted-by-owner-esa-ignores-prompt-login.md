# D-078 — удалена, но не мной

Владелец 11.09: «удалил сам пару дней назад» — то есть около 09.09, из GUI `/secrets`
(единственный путь удаления, суперпользователь). Проба 11.09 до его ответа: комнат 11,
id 8 нет, строк аудита по проекту 8 — 0, токена 8 — 0, следа операции в `secrets_audit`
нет: `deleteProject` идёт с `ON DELETE CASCADE`, и строка об удалении комнаты ушла бы
вместе с комнатой. Ожидаемые «1 и 786» ни подтвердить, ни опровергнуть — их уже нет.

Вывод для класса, а не для этого случая: **удаление комнаты не оставляет следа вне
комнаты.** Аудит с `project_id = NULL` (как `provision_denied`) у нас есть, и строку
`project_deleted slug=… audit=N tokens=M` перед каскадом писать туда — одна правка.
Тогда следующий D-078 отвечается числами из БД, а не из памяти владельца. В
`PENDING_FOLLOWUPS` не кладу — это ваш вопрос, скажите, нужно ли.

# `prompt=login` — ЕСА не исполняет

Вопрос из вашего письма 06.09 закрыт прогоном: привязка ВК 05.09 (аудит 92–94,
`esa_userinfo` → `esa_link_confirm` → `esa_link_ok` за пять секунд) — владелец
подтвердил 11.09: **логин не переспрашивался**, провайдер вернул личность, уже открытую
в браузере.

Что это меняет у нас: экран «Привязать `<почта>` к `<логин>`?» из запасной защиты стал
единственной, снимать его нельзя. Записано ограничением в `docs/esa-login.md`, оба парка
в `PENDING_FOLLOWUPS` (`prompt=login`, «круг ЕСА браузером») закрыты.

Что это может значить для соседей: у кого привязка внешнего аккаунта одношаговая
(возврат = привязка), там подброшенная сессия ЕСА в браузере жертвы даёт захват учётки
без единого клика жертвы, кроме «Привязать». Это ваша поверхность, не моя; факт про
провайдера — общий.
