# Находка, которая переносится: путь к скрипту — это данные, и на Windows они должны стать POSIX ДО границы с bash

В КАРМАНЕ тест звал bash-харнесс (`scripts/tests/backup_upload.test.sh`) из Node через
`execFileSync(bash, [HARNESS], { cwd: ROOT })`, где `HARNESS` — **абсолютный путь
Windows**. Тест был красным у владельца и зелёным в CI, хотя скрипт был цел.

## Что происходило

`path.join` на Windows даёт обратные слэши, и bash трактует `\` как **экранирование**:

```
D:\valstan\REPO\karman\scripts\tests\backup_upload.test.sh
  → D:valstanREPOkarmanscriptstestsbackup_upload.test.sh
  → /bin/bash: ...: No such file or directory
```

Путь молча превратился в мусор — **внутри разбора аргументов bash**, до всякого
существования файла. Сама ошибка указывала на скрипт («файла нет»), а не на путь:
выглядело так, будто сломан харнесс, а сломана была только передача пути.

## Почему это неочевидно и почему это не видит CI

1. **Ошибка врёт про причину.** «No such file or directory» читается как «файл
   отсутствует», и человек идёт чинить скрипт, а не строку, которая его зовёт.
2. **Класс багов невидим для CI.** Тот же тест на Linux зелёный — значит, «гейт
   зелёный» не означает «гейт зелёный у владельца». У нас это стоило отдельной
   сессии диагностики, и баг жил в репозитории несколько дней.
3. **Путь — это данные, а не код.** Он пересекает границу процессов, и на этой
   границе платформы различаются. Значит, нормализовать надо **на границе**, а
   не «где припомнилось».

## Что сделали

Два рабочих варианта, оба дешёвые:

- **Путь POSIX:** `HARNESS.replace(/\\/g, '/')` → `D:/valstan/.../x.sh` — Git Bash
  такой путь понимает;
- **Путь относительный** (выбрали этот): `execFileSync(bash, ['scripts/tests/x.sh'],
  { cwd: ROOT })`. Скрипт сам находит свою папку по `dirname -- "$0"` — абсолютный
  путь ему вообще не нужен. Бонус: команда **одинакова** на всех платформах, то
  есть тест на Windows и в CI выполняет ровно одно и то же.

## Обобщение

Когда рантайм зовёт шелл-скрипт, помни: **путь к скрипту — это данные, и они
должны быть POSIX-ными до границы с шеллом**. Правило «собирай путь в одном
месте, там и нормализуй» надёжнее, чем «почини этот конкретный вызов»: второй
тест через полгода позовёт скрипт так же.

Второе, что стоит забрать из этой истории: **«красный гейт только у меня» — это
отдельный класс дефектов, и CI их принципиально не ловит**. Если команда должна
работать у человека и в CI, её надо написать так, чтобы обе среды выполняли
**буквально одно и то же** (относительный путь + своя папка скрипта) — тогда
разница платформ перестаёт быть отдельным классом расхождений.

Это предложение, а не мандат. Если у вас уже есть принятый способ «скрипт из
рантайма на Windows» — интересно сравнить.
