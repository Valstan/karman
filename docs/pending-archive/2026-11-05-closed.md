проверки, что жив воркер напоминаний. Падение заметит владелец, когда откроет страницу.
Транспорт оповещения уже построен (Telegram-бот напоминаний), поэтому watchdog =
`curl /api/health` + сообщение тем же ботом. ~0.5 сессии.

**Ре-триаж 2026-09-04 (всплыл по возрасту):** возобновлён и **сделан в тот же день**.
`scripts/health_watch.sh` + cron каждые 10 минут: четыре признака (оба юнита активны,
`/api/health` = 200 с телом `ok`, лог бэкапа свежее 36 ч), сообщение в Telegram владельцу
только при СМЕНЕ состояния. `chat_id` кэшируется на диск на каждом прогоне — при мёртвом
Postgres разрешить получателя уже нельзя, а это ровно тот случай, ради которого сторож и
нужен (первая редакция звала разрешение только из отправки, кэш оказался пуст — поймано

**Остаток:** тревога ни разу не срабатывала по-настоящему — учебный прогон висит отдельным

**Ре-триаж 2026-10-05 (всплыл по возрасту):** переформулирован под остаток — сам мониторинг

## G321 в деплое: `ssh karman 'bash -s' "$SHA" "$BASE"` склеивает аргументы — прежняя формулировка

Шаг `ssh karman 'bash -s' "$SHA" "$BASE"` передаёт аргументы склейкой, не argv. Сегодня работает
(оба непустые, без пробелов), но пустой аргумент исчез бы молча, а `BASE` с пробелом
развалился бы на два. Лечение — переменные окружения внутри heredoc
(`ssh karman "SHA=… BASE=… bash -s"` с экранированием) или файл-скрипт по `scp`.

Не сделано 2026-09-05 вместе с G315 намеренно: две правки деплоя без прогона в одном PR —
двойной риск. Признак: `grep -n "bash -s" .github/workflows/deploy-prod.yml` возвращает строки
с позиционными аргументами.

**Ре-триаж 2026-10-19 (всплыл по возрасту, 44 дня):** признак прогнан — две строки (181:
`"$SHA" "$BASE"`, 224: `"$APP_PORT"`), дефект жив; в работу не берём — очередь по-прежнему
занимает аудит #057 (сроки 24.10). Снуз, не парковка: дата расконсервации — ближайшая правка
`deploy-prod.yml`.

зелёный.
