# Промты: библиотека по проектам (заказ владельца 2026-11-06)

> Заказ владельца: «сделай в кармане вкладку промты, разделы по проектам, у
> каждого промта кнопка копировать и кнопка в архив; архив — отдельно, с датой
> создания, и его можно почистить; промты надиктовываются в чат, Мозг их
> раскладывает по проектам». Разбор решения — в ADR репозитория Мозга.

## Что это

Вкладка **«Промты»** на странице `/map` (рядом с вкладками Мозга: Планы,
Серверы, Ферма, Дела владельца, Телефон). Экран поделён пополам: слева —
разделы (проекты) и **названия** промтов, справа — весь выбранный промт целиком.
Текст в списке не показывается. Прокрутка у колонок своя: листая правую, левая
остаётся на месте — видно, какой промт открыт и где ты в списке.

У каждого промта:

- **«Копировать»** — кладёт текст в буфер обмена (дальше он уходит в нейронку);
- **«В архив»** — убирает промт из живого списка, **но не удаляет**: строка
  остаётся в базе с датой архивации;
- **дата создания** — когда промт создан (и когда отправлен в архив).

Архив — отдельный вид того же списка (`/map?tab=prompts&view=archive`): там
промт можно **вернуть** в живые или **удалить** насовсем, а сверху — кнопка
**«Очистить архив»** (и вариант «очистить старше даты»). Чистка архива — ручное
действие, потому что архив имеет свойство разрастаться.

**Разделы** — имена проектов по канону Мозга
(`brain_matrica/docs/PROJECT_NAMES.md`): `MatricaRMZ`, `KARMAN`, `SARAFAN`…
Список разделов живёт в **реестре** (`prompt_project`), а не «посчитывается» из
промтов, — поэтому все разделы экосистемы заведены заранее и видны, даже когда
в них пока пусто. Раздел один на проект: «МАТРИЦА РМЗ» и «MatricaRMZ» — один и
тот же проект, и держать два раздела незачем.

## Почему не в репозитории Мозга

Остальные вкладки карты — это файлы `docs/map/*.md`, которые Мозг правит в
своём репозитории, а КАРМАН читает по GitHub API (токен только на чтение).
Промты в этот ряд не помещаются: у них есть кнопки, которые меняют состояние
(архив, удаление), а писать в репозиторий Мозга из приложения нечем. Поэтому
источник правды — **таблица `prompt`** в БД КАРМАНА, а Мозг кладёт туда
промты через машинный API.

## Канал записи (Мозг → КАРМАН)

`POST /api/prompts` с `Authorization: Bearer $PROMPTS_INGEST_SECRET`:

```json
{ "project": "MatricaRMZ", "title": "ТЗ для кассы", "body": "Напиши ТЗ для кассы…" }
```

- `project` — название раздела (канон: `brain_matrica/docs/PROJECT_NAMES.md`), до 64 символов;
- `title` — необязателен; пусто — берётся первая строка промта;
- `body` — сам промт, до 40 000 символов;
- `part_of` — необязателен: id промта, к которому присоединить этот текст (см. «Пара
  “начитка + план”» ниже).

Ответ: `201` и `{ id, project, title, created_at, merged, part_id }`. Ошибки: `400` (плохое
тело), `401` (чужой токен), `429` (частые запросы), `503` (секрет не задан — канал
выключен).

`GET /api/prompts?project=…&archived=1` — прочитать библиотеку (Мозг
подтягивает промты проекта, когда работает над ним).

`POST /api/prompts/projects` — **синхронизировать разделы**: тело
`{ "projects": ["MatricaRMZ", "KARMAN", …] }` из канона Мозга. Только
добавление: чужие разделы не трогаются и не пропадают (канон может прийти
неполным). Так все разделы экосистемы заводятся заранее — включая пустые.

`POST /api/prompts/rename` — тело `{ "from": "МАТРИЦА РМЗ", "to": "MatricaRMZ" }`:
переименование раздела тянет за собой его промты; если целевой раздел уже есть,
разделы сливаются.

`GET /api/prompts/projects` — текущий список разделов (проверка, что канон доехал).

## Пара «начитка + план» — одна запись (заказ владельца 24.11)

Раньше Мозг складывал надиктованную задачу («начитка») и план к ней **двумя** записями:
проекту приходилось брать раздел и догадываться, какой план к какому промту. По заказу
владельца задача лежит **одним промтом**: тело начитки, пустая строка, тело плана.

**Как это работает.** Хранилище само узнаёт план и присоединяет его к начитке — вторая
запись не появляется:

1. **Явная привязка** — `part_of: <id промта>` в теле POST'а. Точнее всего: так делает
   Мозг, когда знает, к какой задаче относится план.
2. **Ссылка на запись** в тексте плана: «промт #124», «запись #125», «(id 65)». Если
   указанная запись — уже влитый план, текст идёт в его промт (это продолжение задачи).
3. **Дословная цитата** начитки в теле плана («Основание: промт владельца: „…“») — самый
   точный признак пары: чужая задача цитатой не обманет.
4. **Заголовки**: самая близкая начитка по общим словам («План: колонка „Привязка“» ↔
   «Колонка „Привязка“: три цифры договора…»), среди начиток этого проекта, у которых ещё
   нет плана, и не старше трёх часов.

**Продолжение задачи** — запись, которая ссылается на план («Ответы владельца 21.11 по
плану id 65»), — присоединяется к тому промту, где этот план уже живёт.

**Если начитку найти не удалось — план остаётся отдельной записью.** Молча приклеить план
чужой задачи хуже, чем показать владельцу лишнюю запись: лишнее видно и поправимо, а
приклеенный чужой план — тихая порча.

**Ответ POST'а.** Когда текст влит, приходят `id` промта-владельца и `part_id` — id
слитой записи (её можно цитировать в продолжениях задачи) и `merged: true`.

**Проект** получает раздел с уже слитыми промтами: забирает живое, разбирает задачу и
план внутри. Правило «промт и план приходят одним разделом» (ниже) остаётся в силе —
но теперь это один промт, а не две записи рядом.

**Таблица слияний** `prompt_part` (`part_id` → `prompt_id`) помнит, что во что влито:
по ней «у этого промта уже есть план» проверяется без догадок по тексту, и ссылка
«плану id 55» разрешается точно. Миграция `0037_prompt_part.sql`.

**Что сделано с живыми данными (25.11).** 125 записей превратились в 58: 61 пара
(начитка + план), 4 продолжения задачи и 3 дополнения — слиты в своих промтов; два дубля
схлопнуты. Карта пар — в `scripts/merge_prompt_plans.sql` (там же и дамп для отката),
скрипт применён на проде одной транзакцией: `UPDATE 57, DELETE 67`.

**Секрет — отдельный**, а не `HOTLINE_RELAY_SECRET`: промт из библиотеки
копируется в буфер и уходит в нейронку, то есть прямо в рабочий контекст
владельца и его разработчиков. Секрет relay'а знают все бэкенды-участники
комнаты Телефона, и выдавать им право писать в библиотеку промтов незачем.

Значение живёт в env-файле сервиса на боксе (`/etc/karman/karman.env`) и в
хранилище Мозга на машине владельца (`~/.brain_matrica/secrets.env`) — **вне
репозиториев** (D-038). Без переменной эндпоинт отвечает 503, а сама
страница работает: библиотеку можно наполнять и вручную из интерфейса.

## Кто что может

| Действие | Кто |
|---|---|
| Посмотреть библиотеку | **свои** промты (владелец строки) |
| Добавить, архивировать, вернуть, удалить, очистить архив | свои промты (каждый вошедний управляет своей библиотекой) |
| Записать промт через API | машинный канал Мозга (Bearer) — от имени живого аккаунта владельца |

Библиотека **личная**: «информация у каждого аккаунта видна только ему; разделы
и кнопки видны всем; исключение — Круг» (заказ владельца 2026-11-06). Фильтр —
`ownership()` из `lib/auth/rbac.ts`, **без исключения для суперпользователя**:
владелец администрирует аккаунты, но чужие промты не видит — иначе согласие в
Круге было бы декоративным.

Машинный канал (`POST /api/prompts`) пишет от имени **живого аккаунта
владельца** — активного суперпользователя с наименьшим id: сессии у канала нет,
а промт без хозяина не пишется (нет такого аккаунта → 503).

## Схема

Миграции `0025_prompts.sql` (создание) + `0026_prompt_user_id.sql` (личность)
+ `0028_prompt_project.sql` (реестр разделов; ручные, как все):

`prompt`:

| Колонка | Смысл |
|---|---|
| `id` | идентификатор |
| `user_id` | **владелец строки**; NOT NULL, FK на `auth_user` |
| `project` | раздел (название проекта) |
| `title` | короткое имя для списка; пусто — первая строка промта |
| `body` | текст промта — ровно то, что уходит в буфер |
| `source` | `manual` (человек) или `brain` (Мозг) |
| `created_at` | когда создан |
| `archived_at` | когда отправлен в архив; `NULL` — живой |

`prompt_project` — реестр разделов:

| Колонка | Смысл |
|---|---|
| `id` | идентификатор |
| `user_id` | владелец раздела (NOT NULL, FK на `auth_user`) |
| `name` | каноническое имя раздела; UNIQUE (user_id, name) |
| `created_at` | когда заведён |

Нормализация текста при записи — детерминированная (`lib/prompts/normalize.ts`):
CRLF → LF, висячие пробелы, лишние пустые строки. Смысл текста не трогается:
этим занимался Мозг до отправки.

Обе таблицы в бэкапе (`scripts/backup_vault.sh`, `-t prompt -t prompt_project`) — по
прямому заказу владельца: промты сохраняются «на будущее, мало ли где
пригодится — для обучения или для истории».

## Что нужно от владельца (по порядку)

1. Применить `0025_prompts.sql` на проде (`psql -f`; таблица наша, `sudo -n -u
   postgres` не нужен — в отличие от `auth_user`).
2. Положить `PROMPTS_INGEST_SECRET` в env-файл сервиса на боксе и перезапустить
   юнит.
3. Задать то же значение в `~/.brain_matrica/secrets.env` на машине Мозга
   (`PROMPTS_INGEST_SECRET=…`, `PROMPTS_URL=…`) — вне репозитория.
4. Задеплоить этот PR (до 1–2 migration-guard остановит автодеплой красным, и
   это правильно; дальше — `workflow_dispatch`).

## Машинный доступ: проект забирает свой раздел промтов

Заказ владельца (2026-11-08): «научи проекты ходить в Карман и проверять промты
для их проектов, чтобы каждый проект видел именно свои промты, те, которые не в
архиве, новые, и умел забирать их вместе с готовыми планами, анализировать их уже
на основе своих предпочтений и подправлять план, если необходимо, и выполнять
задания… и как-то надо, чтобы эти промты и планы отправлять в архив после их
выполнения, автоматически».

**Два канала, не один.** `/api/prompts` — канал **Мозга**: один секрет
(`PROMPTS_INGEST_SECRET`), пишет от имени владельца. `/api/prompts/section` —
канал **проекта**: у каждого раздела свой токен, проект читает и архивирует
**только свой раздел**.

**Токен раздела.** Имя секрета: `PROMPTS_TOKEN_<Раздел>`, где `<Раздел>` —
каноническое имя раздела из `brain_matrica/docs/PROJECT_NAMES.md` в верхнем
регистре без знаков, кроме букв и цифр: `MatricaRMZ` → `PROMPTS_TOKEN_MATRICARMZ`,
`SARAFAN` → `PROMPTS_TOKEN_SARAFAN`, `trener` → `PROMPTS_TOKEN_TRENER`. Секрет
лежит в **комнате проекта** (vault) и раздаётся проекту тем же каналом, что
остальные секреты комнаты. Раздел приходит в запросе, а **право даёт токен
именно этого раздела**: подставить чужой нельзя — секрет другого раздела не
совпадёт.

**Куда класть токен и куда предлагать выдачу.** Сервис читает свои секреты из комнаты,
которую видит по своему `SECRETS_TOKEN` (на боевой машине это `karman-hotline`, а **не**
`karman`). Поэтому: **значение токена живёт в комнате проекта**, а **выдачу в адрес
сервиса предлагаем в комнату, которую сервис реально читает** — грант в другую комнату
сервис не прочитает, и выдача останется висеть непринятой. Проверяется одной read-only
пробой «что сервис видит» до выдачи, а не доверием инструкции. Секрет раздела самого
сервиса (`KARMAN`) лежит в комнате сервиса и выдачи не требует вовсе.

#### Программа, которая архивирует чужие разделы (27.11)

Отдельный случай, который ловится на живых данных: **программа-оболочка ведёт области
чужих проектов** и архивирует их разделы по кнопке. Ей нужен токен раздела **в своей
комнате** — а не в комнате проекта и не в комнате сервиса. Отсюда **две выдачи на один
ключ**:

```
комната проекта  ──выдача──▶  комната программы   (программа архивирует)
      │
      └──выдача──▶  комната сервиса             (сервис сверяет токен)
```

Значение одно и то же (своей записью владеет комната проекта), а выдачи нужны две:
без второй программа получит `503` («канал не настроен»), без первой — `403`.

**Политика приёма** объявляет комната-получатель — один раз на тройку
(получатель, источник, ключ): `POST /api/secrets/policies`. Тогда проект может
предложить свою выдачу **одним запросом**, и она принимается сразу (`autoAccept`),
без второй руки. Пока политики нет, предложение висит `pending` и ждёт ручного
`accept` — и при следующей ротации токена повторится.

⚠️ **Выдача отдаёт значение только из СВОЕЙ записи источника.** Если источник сам
получил ключ по чужой выдаче, своей записи у него нет — и его выдача получателю
**не принесёт значения**: выдача оформится и будет `active`, а ключа не будет.
Молчаливая ловушка, и вдобавок она **занимает имя**: вторая выдача под тем же именем
в ту же комнату получит `409` — то есть перекрёсток блокирует правильный путь.
Проверено приёмкой (`lib/services/secrets.test.ts`): «выдача отдаёт значение только из
СВОЕЙ записи источника» и «выдача от перекрёстка занимает имя и блокирует правильный
путь». Если источник недоступен (паспортный вход, read-only токен, запрет читать
комнату руками) — предложение делает **сам проект**, а не посредник.

### Контракт

`GET /api/prompts/section?project=<Раздел>&archived=1`

- `archived=1` — архивные промты раздела; без параметра (или `archived=0`) —
  **живые, свежие сверху** (то, что проект и должен делать: новые, не в архиве);
- заголовок `Authorization: Bearer <токен раздела>`;
- ответ: `{ "project": "<Раздел>", "prompts": [ { id, project, title, body, source, createdAt, archivedAt } ] }`.

`POST /api/prompts/section`

- тело: `{ "project": "<Раздел>", "id": <number>, "archived": true }` — отправить
  промт в архив; `archived: false` — вернуть из архива;
- ответ: `{ "ok": true, "project": "<Раздел>", "id": <number>, "archived": true }`.

Коды ответа: `200` — ок; `400` — плохой `id`; `403` — токен не от этого раздела;
`404` — такого промта в разделе нет; `429` — частые запросы; `503` — секрет
раздела не задан (канал не настроен).

### Правила, которые живут на стороне проекта

1. **Проект читает свой раздел — и только его.** Раздел другой не виден и не
   архивируется.
2. **Промт и план приходят одним разделом.** В библиотеке задача лежит **одним промтом**:
   тело начитки, пустая строка, тело плана (заказ владельца 24.11). Проект забирает живое
   и разбирает: что за задача, какой план приложен внутри.
3. **План уточняется под проект, а не выдумывается.** Проект сверяет план со
   своими предпочтениями и кодом и правит план (или пишет, почему оставил как
   есть) — **в записи плана в своей копии работы**, а не в библиотеке: план в
   библиотеке — это задание владельца.
4. **Архив = «сделано».** Промт уходит в архив **после выполнения**, тем же
   вызовом POST. Не выполнено — не архивировать: следующая сессия подхватит.
   Архив можно вернуть (`archived: false`) — это не удаление.
5. **Тише не значит «не сделано»:** если задача не выполнена, промт остаётся
   живым и виден владельцу в списке раздела.

### Что делает Мозг

Мозг складывает промты и планы по разделам (`/api/prompts`), выдаёт проекту
токен его раздела и **не архивирует за проект**: архивирует тот, кто выполнил.
Если проект молчит — промт остаётся живым, и это видно.
