# Ночной бэкап vault: 23 ночи без архива (09.10 — 31.10)

**Найдено 02.11 при сверке прод-фактов после аудита #057. Прод-уровень: P1.**

## Что обнаружено

На Яндекс.Диске в папке бэкапов (`BACKUP_WEBDAV_DIR`, по умолчанию `/KARMAN-backups`)
лежит **41 архив**, а длинный ряд выглядит так:

```
20260830 20260831 20260901 … 20261001 [20261002 нет] 20261003 … 20261008
                                                    ← 20261009 … 20261031 НЕТ (23 ночи) →
                                                                  20261101 20261102
```

То есть **с 9 октября по 31 октября архивов не было ни одного** — 23 ночи подряд. Единственная
другая дыра — 2 октября (одна ночь).

Лог бэкапа (`~/backups/vault-backup.log`) при этом писался каждую ночь и показывал ровно
это:

```
backup_vault: выгрузка karman-vault-20261026-003002.tar.gpg на Яндекс.Диск…
curl: (56) Recv failure: Connection reset by peer
backup_vault: выгрузка karman-vault-20261027-003002.tar.gpg на Яндекс.Диск…
curl: (52) Empty reply from server
backup_vault: выгрузка karman-vault-20261028-003002.tar.gpg на Яндекс.Диск…
curl: (22) The requested URL returned error: 500
… 29.10 (56) ×2, 30.10 (52), 31.10 Terminated, 01.11 (52), 02.11 (52)
```

## Почему это не заметил сторож

Сторож (`scripts/health_watch.sh`) проверяет **свежесть лога бэкапа** (запись за последние
36 ч) — и лог писался каждую ночь, потому что скрипт начинает работу до выгрузки. То есть
критерий «бэкап был» на практике означал «скрипт бэкапа запускался», а не «архив лежит на
Диске». С 9 октября по 31 октября этот критерий был зелёным при полном отсутствии
бэкапов.

Вторая причина: **проверка размера выгруженного файла недостижима.** В `backup_vault.sh`
выгрузка идёт под `set -euo pipefail`:

```bash
wd -T "$WORK/${NAME}.tar.gpg" "${WEBDAV_HOST}${WEBDAV_DIR}/${NAME}.tar.gpg"   # ← упало → скрипт умер
# … а сверка размера — ниже, и до неё выполнение не доходит:
REMOTE_BYTES=$(wd -I … )   # «успешный PUT ≠ „на Диске целый файл“»
```

То есть ровно тот случай, ради которого сверка и написана (обрыв на середине даёт
«существующий» бэкап вплоть до дня восстановления), сценарий обрыва и обрывал саму
сверку.

## Что landed, а что нет — и почему расхождение

01.11 и 02.11 curl тоже ругался (52 / Empty reply), но **файлы на Диске есть**:
`karman-vault-20261102-003001.tar.gpg`, HTTP 200, Content-Length 105 444 101, Last-Modified
`2026-11-02 02:17:27 GMT` — то есть сервер дописал файл уже после того, как клиент сдался
(клиент отвалился в 01:53 UTC, сервер закончил в 02:17 UTC). Значит:

- с 09.10 по 31.10 — **не дошло ничего** (23 ночи без бэкапа);
- с 01.11 — **доходит**, но клиент считает это ошибкой и валит скрипт;
- размер архива — **105 МБ**, выгрузка занимает ~1 ч 45 мин; соединение с
  `webdav.yandex.ru` с бокса держится на грани, отсюда и 52/56/500.

Скорость выгрузки — отдельная тема: 105 МБ за ~105 минут — это ~17 КБ/с. Пока архив
такого размера уезжает по такой связи, «просто повторить» — единственный честный ответ.

## Что предложено сделать (три части, вместе)

1. **Выгрузка — с повтором и сверкой, которая не теряется.** Не ронять скрипт на
   неудачном `curl`: поймать код возврата, сделать ещё одну попытку, и **в любом случае**
   дойти до сверки размера (`HEAD`). Если размер совпал — выгрузка успешна (клиентский
   код ошибки был ложным). Если не совпал — **оставить локальную копию архива** и поднять
   тревогу: сейчас локальный файл удаляется вместе с временным каталогом, и при обрыве
   архив пропадает совсем.
2. **Сторож — проверять архив, а не лог.** Критерий «бэкап был» = «за сегодня/вчера есть
   архив на Диске» (или подтверждённая отметка от скрипта). Свежесть лога остаётся
   вторым, отдельным признаком («задание вообще запускалось»).
3. **Тихий сдвиг границы.** Дыра в 23 ночи — это не «сбой», а «не было теста на то, что
   бэкап доехал». Значит, нужен **признак, который можно прогнать в минуту** и который
   падает на отсутствии архива, — иначе следующий такой месяц пройдёт так же.

## Эскиз правки (готов к применению, но не применён молча)

**1. `scripts/backup_vault.sh` — выгрузка, которая не теряет сверку.** Сейчас:

```bash
wd -T "$WORK/${NAME}.tar.gpg" "${WEBDAV_HOST}${WEBDAV_DIR}/${NAME}.tar.gpg"
```

Заменить на (код возврата не роняет скрипт, сверка выполняется ВСЕГДА, одна повторная
попытка, при неудаче остаётся локальная копия):

```bash
upload() {
  set +e
  wd -T "$WORK/${NAME}.tar.gpg" "${WEBDAV_HOST}${WEBDAV_DIR}/${NAME}.tar.gpg" 2>/dev/null
  local rc=$?
  set -e
  remote_bytes() {
    wd -I "${WEBDAV_HOST}${WEBDAV_DIR}/${NAME}.tar.gpg" 2>/dev/null \
      | tr -d '\r' | awk 'tolower($1) == "content-length:" { print $2 }' | tail -1
  }
  local local_bytes; local_bytes="$(stat -c %s "$WORK/${NAME}.tar.gpg")"
  local remote; remote="$(remote_bytes)"
  if [ -n "$remote" ] && [ "$remote" = "$local_bytes" ]; then
    echo "backup_vault: выгрузка подтверждена размером (${local_bytes} Б), код curl=$rc"
    return 0
  fi
  if [ "$rc" = "0" ] && [ -z "$remote" ]; then
    echo "backup_vault: ВНИМАНИЕ — размер проверить не удалось (сервер не отдал Content-Length)" >&2
  fi
  return 1
}

if ! upload; then
  echo "backup_vault: выгрузка не подтверждена — повторяю один раз…" >&2
  if ! upload; then
    # Архив не выгружен: сохраняем локально, чтобы он не пропал вместе с WORK,
    # и поднимаем тревогу с путём к файлу.
    mkdir -p "${BACKUP_KEEP_DIR:-$HOME/backups/pending}"
    cp -f "$WORK/${NAME}.tar.gpg" "${BACKUP_KEEP_DIR:-$HOME/backups/pending}/" || true
    die "выгрузка не удалась (дважды); локальная копия — ${BACKUP_KEEP_DIR:-$HOME/backups/pending}/${NAME}.tar.gpg"
  fi
fi
```

**2. `scripts/health_watch.sh` — сторож смотрит на архив, а не на лог.** Сейчас критерий
«бэкап был» = «лог бэкапа свежий» (строка ~160). Нужно добавить второй признак: есть ли
архив за сегодня/вчера. Дёшево и без сети — **отметка от скрипта**: после подтверждённой
выгрузки писать `$HOME/.karman-health/backup-ok-YYYYMMDD` (или отдельный каталог), а
сторожу проверять наличие отметки за сегодня/вчера. Тогда:

- отметки нет → «бэкап vault не подтверждён» (ровно тот сигнал, которого не было 23 ночи);
- отметка есть → всё в порядке, и она означает «размер сошёлся», а не «скрипт запускался».

Альтернатива (если отметки не хочется) — `PROPFIND` по `BACKUP_WEBDAV_DIR` раз в сутки с
кэшем: «есть ли `karman-vault-<вчера>*.tar.gpg`». Минус: лишняя сеть в стороже, который
и так ходит к Диску раз в ~105 минут.

**3. Признак, который можно прогнать за минуту.** Сейчас у класса нет признака вообще —
поэтому дыра длилась 23 ночи. Признак: список архивов на Диске (`PROPFIND` глубиной 1,
имена `karman-vault-*.tar.gpg`) — и ожидание «за сегодня и вчера есть». Он же ложится в
PENDING как periodic.

## Чего этот документ НЕ делает

Не чинит и не запускает: ручная выкачка сейчас (105 МБ и ~2 часа, запись в облако
владельца) — решение владельца, и она не нужна, чтобы понять причину. Правка скриптов
требует боевой проверки (запуск ночного бэкапа), поэтому она вынесена в PENDING отдельным
пунктом, а не сделана молча.
