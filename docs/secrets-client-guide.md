# Менеджер секретов KARMAN — гайд для проекта-клиента

Как любому проекту экосистемы хранить свои секреты в зашифрованном менеджере KARMAN
и читать их обратно — по своему токену, без участия человека в рантайме. Прочитав
этот файл, агент любого проекта может подключиться к **своей** комнате.

## Идея

- У каждого проекта — **своя «комната»** (project) в KARMAN. Секреты лежат
  **зашифрованными** (AES-256-GCM, мастер-ключ только в env сервера KARMAN).
- Проект ходит к API по **Bearer-токену**: read-write токен умеет и сохранять, и читать.
- **Токен = удостоверение комнаты.** Он заскоуплен **только на свою комнату** — по нему
  нельзя прочитать или перезаписать чужие секреты. Знать slug/id комнаты для работы не нужно:
  токен сам приводит запрос в нужную комнату.

Базовый URL менеджера владелец выдаёт вместе с токеном; ниже по тексту он обозначен как
`$VAULT_URL` — экспортируйте его один раз (`export VAULT_URL=https://…`), и примеры
заработают как есть. Переменная, а не сам адрес, по простой причине: репозиторий публичный,
а адрес хранилища секретов экосистемы в публичный репозиторий не кладём.

## Каждому проекту — своя комната

У каждого проекта экосистемы — **своя комната**, и знать её slug для подключения **не нужно**:
slug — лишь человекочитаемая метка в UI владельца, а в нужную комнату запрос приводит сам токен.
Актуальный список комнат (он же источник истины) владелец видит на странице `/secrets`; новая
комната заводится self-serve (ниже) или владельцем там же.

## Каким путём онбордиться: паспорт по умолчанию

Решение владельца D-061 (01.09.2026, реестр решений — `brain_matrica/docs/DECISIONS.md`):
**ключи ходят без рук владельца**, владелец только командует.
Порядок выбора пути для любого следующего проекта — сверху вниз, первый подходящий:

1. **Паспорт** (ниже) — есть CI с OIDC. Штатный путь, ручной передачи значения нет вовсе.
2. **Времянка** — CI с OIDC нет, а комната уже наполнена (self-serve упрётся в `409`).
3. **Break-glass по общему ключу** — аварийный, держится на общей строке.
4. **Ручная выдача владельцем** — последний запасной путь, а не «как обычно».

Ручная передача токена в чат/диктовкой — исход для случая, когда первые три недоступны, и его
надо уметь назвать вслух. Онбординг проекта с рабочим GitHub Actions ручной выдачей — регресс.

## Паспортный вход (штатный путь с волны 2 ADR-0012)

Если у проекта есть CI с OIDC — **никакой общей строки не нужно**: воркфлоу предъявляет
подписанное удостоверение своего репозитория и получает короткоживущий токен своей комнаты.

```bash
# в GitHub Actions, permissions: id-token: write
ASSERTION="$(curl -sf -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN"   "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=karman-vault" | jq -r .value)"
curl -sf -X POST "$VAULT_URL/api/secrets/session"   -H "Authorization: Bearer $ASSERTION"
# → 201 {"ok":true,"token":"skm_…","expiresAt":"…","slug":"myproject","canWrite":false}
```

Дальше — обычный API ниже, `SECRETS_TOKEN` = полученный `token`. Личность должна быть заведена
владельцем в реестре один раз (`403` = «личность не зарегистрирована»); комната автоматически
**не заводится**. Своя интроспекция — `GET /api/secrets/self`, самоотзыв — `DELETE /api/secrets/session`.
Полный контракт и рецепт — `docs/passport-server.md`.

Три грабли, на которые наступил второй потребитель паспорта (не первый — первому было очевидно):

- **Токен приходит ответом `/session`, а не из `secrets` репозитория** — GitHub его сам
  **не маскирует**, а логи публичного репозитория публичны. `echo "::add-mask::$TOKEN"` ставится
  руками и **до первого использования** токена; маскировать и удостоверение (`$ASSERTION`), и токен.
- **Второй `trap … EXIT` в том же шаге молча заменяет первый.** Trap на уборку временного файла,
  поставленный после trap'а самоотзыва, убивает самоотзыв — сессия живёт до конца TTL. Одна
  функция на все действия, один `trap` на шаг.
- **`tokenPrefix` (`skm_…`) печатается в открытый лог** ответом `/session` и `/claim`. Секретом
  он не является, но аудит комнаты сопоставляет сессии по префиксу: посторонний с логом сможет
  читать эту связь. Не нужно — не печатайте ответ целиком, берите `jq -r .token`.

## Времянка: одноразовый код → ваш токен (когда токена ещё нет)

Ситуация: комната уже наполнена владельцем, поэтому self-serve её не откроет (`409`), а CI
с OIDC у вас нет — значит и паспорт не подходит. Тогда владелец выпускает **времянку**:
одноразовый код `skb_…`, который живёт минуты и гаснет в момент обмена. Его не страшно
продиктовать или прислать в чат — настоящий токен по нему заберёте вы сами.

```bash
curl -fsS -X POST "$VAULT_URL/api/secrets/claim"   -H "Authorization: Bearer skb_<код-от-владельца>"
# → 201 {"ok":true,"token":"skm_...","tokenPrefix":"skm_...","slug":"myproject","canWrite":false}
```

- Обменять код можно **ровно один раз**. Второй запрос — `401`, и это не ошибка сети:
  если ваш обмен не прошёл, а код был жив, значит его использовал кто-то другой — скажите
  владельцу, он отзовёт выданный токен.
- Все отказы выглядят одинаково (`401`): неизвестный, истёкший, отозванный и уже обменянный
  код снаружи неразличимы. Причина видна владельцу в аудите комнаты.
- Полученный `token` — обычный токен комнаты **без срока**: сразу кладите его в рантайм-env
  (`SECRETS_TOKEN`) и дальше работайте по обычному API ниже. В чат его не возвращайте.

## Self-serve onboarding по общему ключу (break-glass)

> С волны 2 ADR-0012 этот путь — **аварийный**, а не штатный: он держится на общей строке,
> которая ничего не говорит о предъявителе. Владелец может погасить его переменной
> `PROVISION_KEY_ENABLED=false` (тогда роут отвечает `503`).

Мандат brain 2026-07-12 (амендмент §6 ADR-0006): новая проектная сессия заводит свою комнату
**сама**, без кликов владельца в MFA-UI. Нужен **provisioning-ключ** `VAULT_PROVISION_KEY`
(секрет #008-класса, у brain/владельца; читать чужие ячейки или выпускать токены к живым
комнатам им нельзя).

```bash
curl -X POST "$VAULT_URL/api/secrets/provision" \
  -H "Authorization: Bearer $VAULT_PROVISION_KEY" \
  -H "Content-Type: application/json" \
  -d '{"slug":"myproject","name":"MyProject"}'
# → 201 {"ok":true,"projectId":N,"slug":"myproject","token":"skm_…","tokenPrefix":"skm_…"}
```

- `slug` — латиница/цифры/дефис (метка комнаты в UI); `name` опционален (по умолчанию = slug).
- `token` в ответе — **read-write токен комнаты, показывается ОДИН раз**: сразу положи его
  в рантайм-секрет проекта (`SECRETS_TOKEN`) и дальше работай по обычному API ниже.
- **Комната уже существует?** Не тупик (ADR-0010): если она **пуста** (0 секретов, 0 карточек)
  и ни один её токен ни разу не использовался — тот же `POST` выпустит **первый рабочий
  rw-токен** (`201`, старые невостребованные токены отзываются, аудит `provision_first_token`).
  Так онбордится комната, которую завели заранее, а токен потерялся при доставке.
- Коды: `201` создано / первый токен выдан; `409` комната живая — в ней есть секреты, карточки
  или использованный токен (токен НЕ выдаётся — переоткрытие только владельцем под 2FA);
  `401` неверный provisioning-ключ; `503` provisioning не сконфигурирован на сервере.
- Каждая операция (включая отказы) пишется в аудит-лог комнаты/сервиса.

## Онбординг через владельца (запасной путь)

1. Владелец выдаёт твоему проекту **read-write токен** (KARMAN → `/secrets` → твоя комната →
   Токены). Токен показывается **один раз** — владелец передаёт его тебе разово (paste-message).
2. Положи токен в **рантайм-секрет проекта** — env-переменную `SECRETS_TOKEN` (или секрет-стор
   деплоя/CI). **НИКОГДА не коммить в git** (ни в версионируемый `.env`, ни в код).
3. Сделай smoke-проверку (ниже) — пустая комната вернёт `200 {"secrets":{}}`.
4. Дальше сохраняй/читай свои секреты по API.

Токены, выданные владельцем, **без срока** (не истекают). Ротация — ручная: если токен утёк/
потерян, попроси владельца отозвать старый и выдать новый в `/secrets`. Токены паспортной сессии,
наоборот, **со сроком** (`expiresAt`, по умолчанию час) и гасятся сами — ротация там сводится
к перезапуску деплоя.

## Первое подключение (smoke)

```bash
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $SECRETS_TOKEN" \
  "$VAULT_URL/api/secrets"
# 200 — токен валиден (пустая комната вернёт {"secrets":{}}); 401 — токен битый/отозван.
```

## Сохранить свои секреты (POST, bulk upsert)

```bash
curl -X POST "$VAULT_URL/api/secrets" \
  -H "Authorization: Bearer $SECRETS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"secrets":{"DB_PASSWORD":"…","SOME_API_KEY":"…"}}'
# → {"ok":true,"written":2}
```

## Прочитать обратно (GET)

```bash
# все секреты проекта:
curl -H "Authorization: Bearer $SECRETS_TOKEN" "$VAULT_URL/api/secrets"
# → {"secrets":{"DB_PASSWORD":"…","SOME_API_KEY":"…"}}

# один ключ:
curl -H "Authorization: Bearer $SECRETS_TOKEN" \
  "$VAULT_URL/api/secrets?key=DB_PASSWORD"
```

## Node-сниппет

```js
const BASE = `${process.env.VAULT_URL}/api/secrets`;
const headers = {
  Authorization: `Bearer ${process.env.SECRETS_TOKEN}`,
  'Content-Type': 'application/json',
};

export async function saveSecrets(secrets) {
  const r = await fetch(BASE, { method: 'POST', headers, body: JSON.stringify({ secrets }) });
  if (!r.ok) throw new Error(`secrets save failed: ${r.status} ${await r.text()}`);
  return r.json(); // { ok, written }
}

export async function loadSecrets() {
  const r = await fetch(BASE, { headers });
  if (!r.ok) throw new Error(`secrets load failed: ${r.status} ${await r.text()}`);
  return (await r.json()).secrets; // { KEY: value, ... }
}
```

## Python-сниппет

```python
import os, requests

BASE = os.environ["VAULT_URL"] + "/api/secrets"
HEADERS = {"Authorization": f"Bearer {os.environ['SECRETS_TOKEN']}"}

def save_secrets(secrets: dict) -> dict:
    r = requests.post(BASE, headers=HEADERS, json={"secrets": secrets}, timeout=10)
    r.raise_for_status()
    return r.json()  # {"ok": True, "written": N}

def load_secrets() -> dict:
    r = requests.get(BASE, headers=HEADERS, timeout=10)
    r.raise_for_status()
    return r.json()["secrets"]  # {"KEY": "value", ...}
```

Типичный паттерн «восстановить, если потерял локальную копию»:

```js
let local = readLocalEnvSomehow();
if (!local || Object.keys(local).length === 0) {
  local = await loadSecrets(); // подтянуть из менеджера
}
```

## Ключ, общий с другим проектом (выданный доступ)

Если один и тот же ключ нужен двум проектам, **копировать его между комнатами не надо** —
владелец комнаты-источника выдаёт вашей комнате доступ к этому ключу. Значение остаётся
в одном месте, вы читаете его **своим обычным токеном**, под именем, о котором договорились:

```bash
curl -H "Authorization: Bearer $SECRETS_TOKEN" \
  "$VAULT_URL/api/secrets?key=VMALMYZHE_INGEST_KEY"
# → {"secrets":{"VMALMYZHE_INGEST_KEY":"…"}}
```

Со стороны клиента ничего нового: выданные ключи приходят в тот же `GET /api/secrets`
вперемешку со своими, отличать их не нужно. Что стоит знать:

- **Пока выдачи нет (или ключ ещё не заведён в источнике) — `404`.** Это нормальное
  состояние ожидания: как только ключ появится, тот же запрос начнёт отдавать `200`,
  менять на вашей стороне ничего не нужно.
- **Записать такой ключ через `POST` нельзя — `403`.** Он принадлежит комнате-источнику;
  ротацию делает её владелец, вы сразу получаете новое значение.
- **Доступ отзываем** без смены самого секрета: после отзыва ключ снова даёт `404`.
- Каждое ваше чтение видно в аудите комнаты-источника — выдача не бывает молчаливой.

Запросить общий ключ — через brain (решение владельца) или напрямую у комнаты-источника:
нужны имя ключа у источника, ваша комната и имя, под которым вы хотите его видеть.

### Выдать свой ключ другой комнате — без владельца (D-061)

Если ключ ваш и решение о выдаче есть — выдаёте сами, **токеном своей комнаты с правом
записи**. Сессия владельца-человека не нужна; комната-получатель этим путём выдать себе
ничего не может — полномочие остаётся у владельца данных.

```bash
# выдать: свой ключ VK_TOKEN → комнате dkmalmyzh под тем же именем
curl -sf -X POST "$VAULT_URL/api/secrets/grants" \
  -H "Authorization: Bearer $SECRETS_TOKEN" -H "Content-Type: application/json" \
  --data-binary @grant.json
# grant.json: {"key":"VK_TOKEN","target_slug":"dkmalmyzh","note":"D-061, решение Мозга 02.09"}
# → 201 {"ok":true,"id":12,"source":"setka","target":"dkmalmyzh","key":"VK_TOKEN","alias":"VK_TOKEN"}

# что выдано (id нужен для отзыва):
curl -sf "$VAULT_URL/api/secrets/grants" -H "Authorization: Bearer $SECRETS_TOKEN"
# → {"slug":"setka","issued":[{"id":12,"sourceKey":"VK_TOKEN","targetSlug":"dkmalmyzh",...}]}

# отозвать:
curl -sf -X DELETE "$VAULT_URL/api/secrets/grants" \
  -H "Authorization: Bearer $SECRETS_TOKEN" -H "Content-Type: application/json" \
  --data-binary '{"id":12}'
```

- `alias` — имя, под которым получатель увидит ключ (по умолчанию — то же). `note` —
  **основание, обязательно**: номер решения или причина; уходит в аудит обеих комнат.
- В аудите принципал — `room:<ваш slug>`, а не владелец; чем предъявились (паспорт или токен) —
  в тексте строки. Отзыв владельцем из GUI работает как прежде.
- Коды: `403` — токен только для чтения (раздавать свои ключи может только пишущий);
  `404` — нет такой комнаты-получателя или чужая выдача при отзыве; `409` — у получателя
  свой ключ с таким именем / выдача уже есть / выдача уже отозвана.
- Компрометация вашего токена = возможность раздать ваши ключи другим комнатам. Это та же
  граница, что у записи: пишущий токен и так переписывает ваши секреты. Отзыв токена гасит
  и этот путь; выдачи, сделанные до отзыва, видны в `GET` и в аудите — снимайте их там.

## SSH-ключи к продам: комната вместо диска (D-035)

Решение владельца [D-035]: **новая машина больше не генерирует SSH-ключ и не относит его
на прод руками.** Ключи владельца зеркалируются в комнатах КАРМАНа, новая машина берёт
свой ключ из комнаты **в `ssh-agent`, а не на диск**.

Честная граница: один секрет на новую машину всё равно приносится руками — **токен комнаты**.
Это один секрет вместо пяти ключей, а не ноль. И vault здесь — **копия и канал доставки**;
источник истины доступа по-прежнему `authorized_keys` на боксе.

### Конвенция имён

| Имя ключа | Что лежит |
|---|---|
| `SSH_KEY__<alias>__<machine>` | приватный ключ, PEM как есть, с переводами строк |
| `SSH_PUB__<alias>__<machine>` | публичная половина (чтобы `authorized_keys` собирался из комнаты, а не с диска машины) |

- `<alias>` — ssh-алиас прода, `<machine>` — имя машины, с которой ходят. Из имени обязаны
  читаться оба: ключи остаются **по-машинными**, общий ключ на все машины не заводим,
  и отзыв по имени поэтому не теряется.
- **Дефис в алиасе не пройдёт.** Имя ключа валидируется как env-переменная
  (`^[A-Za-z_][A-Za-z0-9_]*$`) — дефисы и точки заменяйте на `_`, разделитель между
  частями — двойное подчёркивание.

### Забрать ключ в агент (не на диск)

```bash
curl -fsS -H "Authorization: Bearer $SECRETS_TOKEN" "$VAULT_URL/api/secrets?key=SSH_KEY__myprod__PC79"   | jq -r '.secrets.SSH_KEY__myprod__PC79' | ssh-add -
```

Ключ попадает в агент на время сессии и **не печатается** — ИИ-агент, работающий в этой
консоли, его не видит. `ssh-add -l` покажет отпечаток, но не материал.

Нужен постоянный доступ (машина ваша, не общая) — тогда на диск, но без вывода в консоль
и сразу с правами:

```bash
umask 077
curl -fsS -H "Authorization: Bearer $SECRETS_TOKEN" "$VAULT_URL/api/secrets?key=SSH_KEY__myprod__PC79"   | jq -r '.secrets.SSH_KEY__myprod__PC79' > ~/.ssh/id_myprod
chmod 600 ~/.ssh/id_myprod
ssh-keygen -y -f ~/.ssh/id_myprod > /dev/null && echo "ключ читается"
```

Последняя строка — приёмка: `ssh-keygen -y` разбирает ключ по-настоящему и падает на
испорченном. Она нужна именно здесь, см. ниже.

### Переводы строк: проверено, а не обещано

Многострочное значение — классическое место, где ключ ломается молча. Что проверено
на нашей стороне:

- **Хранение и отдача.** Значение секрета не проходит `trim()` и не нормализуется;
  кап — 64 КБ (ed25519 ~400 Б, RSA-4096 ~3.4 КБ). В `GET /api/secrets` значение уезжает
  обычной JSON-строкой с `
`, `jq -r` возвращает исходный текст байт-в-байт.
- **Ввод через GUI — здесь была настоящая дыра, закрыта 2026-08-25.** Поле значения было
  однострочным `<input type="password">`, а такой input по спеке HTML применяет *value
  sanitization algorithm* и **молча вырезает переводы строк** из вставленного текста.
  Приватный ключ, вставленный в форму, стал бы одной строкой без единой ошибки — и узнали
  бы об этом только при первом `ssh`. Теперь поле многострочное.

Поэтому `ssh-keygen -y -f <файл>` в приёмке выше — не формальность: это единственная
проверка, которая отличает целый ключ от склеенного.

### Что остаётся ходом владельца

Завести ключ в комнату и снять с ревизии мёртвые — операция владельца в GUI vault'а.
Реестр выданного ведёт brain (`access/INDEX`), сверка — на quarterly.

## Правила и коды

- Имя ключа — как env-переменная: `^[A-Za-z_][A-Za-z0-9_]*$`. Значение ≤ 64 КБ, до 200 ключей за POST.
- Запись — upsert (повторный POST с тем же ключом перезапишет значение). Удаление секрета — только
  владелец в UI (по токену удаления нет).
- Коды: `200` ок; `400` плохое тело; `401` нет/недействителен токен; `403` токен только для чтения
  (нужен read-write) **или** попытка записать ключ, приходящий по выданному доступу; `404` нет
  ключа (GET ?key=); `409` конфликт выдачи (`/grants`); `429` слишком часто (лимит ~60/мин).
- Сами значения наружу видны только по валидному токену; в логах/ответах об ошибках их нет.
