## Текущая нитка

**Минимакс: надёжность расписания ежесуточного забора (находка 18.11 после деплоя).** Живая
проверка показала: воркер поднялся, а обхода за сутки не было — ни одной строки
`[minimax/daily-bonus]` в журнале приложения. Три причины, все в расписании:

1. **«Догон» при старте воркера был мёртвым кодом.** Функция «сколько до 05:00 МСК» у уже
   прошедшего часа откатывалась на сутки вперёд, поэтому `delay <= 0` не наступало НИКОГДА.
   А воркер после деплоя поднимается раньше, чем приложение слушает порт (в логе:
   `dispatch error fetch failed`, `reconcile error fetch failed`) — то есть даже живой «догон»
   упал бы в первый запуск.
2. **Упавший забор ждал до следующего дня** — единственный заход за сутки просто терялся, и у
   провисших аккаунтов клетка вендора не сдвигалась (серия дней рвалась).
3. **Один сбойный аккаунт убивал весь обход** — тело аккаунта в `sweepDailyBonus` шло без
   `try/catch`.

**Что сделано в этом PR:**

- **Догон по факту «час забора наступил»** (`dailyBonusTimePassed`) — отдельная проверка вместо
  мёртвого `delay <= 0`.
- **Повтор через 5 минут** при неудаче вместо ожидания до завтра
  (`MINIMAX_DAILY_BONUS_RETRY_MS`).
- **Маркер «обход за московские сутки уже был»** — файл в каталоге состояния воркера
  (`KARMAN_WORKER_STATE_DIR`, по умолчанию `~/.local/state/karman`): без него каждый рестарт
  воркера дёргал бы вендора заново (забор по ~136 аккаунтам), а владелец просил держать нагрузку
  на MiniMax разумной.
- **Сбойный аккаунт больше не обрывает обход** — `try/catch` на тело аккаунта, сбой считается
  неудачей (`report.failed`), обход идёт дальше.
- **Циклы воркера поднимаются только когда файл запущен как программа** (`isEntryPoint`), чистые
  помощники расписания экспортированы — их можно тестировать.

**Что осталось (честно):** маркер ставится по ответу роута, а обход идёт в фоне — если он
начнётся и умрёт посередине (упала БД), маркер уже записан, а часть аккаунтов останется без
строки леджера за сутки. Чинится статус-эндпоинтом (GET → «обход завершён» + неудавшие) и
повтором только по ним; пункт в `docs/PENDING_FOLLOWUPS.md`.

## Failed approaches (этой нитки)

- **Первый пересчёт расхождения модели с панелью был с ошибкой в SQL** (16.11: «клетка
  расходится у 73 из 109, класс у 48»): серия считалась как «сколько отметок за 7 дней»,
  а не как серия дней подряд. Правильный пересчёт — 42 из 112 и 3. Надёжный способ —
  сверять модель с внешней правдой ТОЙ ЖЕ формулой, какой считает код, иначе цифры
  выглядят правдоподобно и совсем не про то.
- **Состояние панели в памяти процесса** — не переживало рестарт и разъезжалось между
  чанками Turbopack: action и страница видели разное состояние одних и тех же
  аккаунтов. Теперь состояние в БД.
- **Проверка панели только для выбранного кандидата** — так аккаунт, у которого очки
  появились, в оборот не возвращался: его отсекала эвристика раньше, чем до панели
  доходила очередь. Теперь панель решает доступность заранее.
- **`activateAccount` возвращал `true` при проигранном CAS** — `return false` стоял
  внутри транзакции, наружу уходил `true`. Теперь результат транзакции возвращается
  наружу.
- **«24 часа от активации» как граница** — грубо: аккаунт, активированный в 23:50, ждал бы
  целые сутки, хотя сброс ночной. Заменено ночной границей (`DAILY_RESET_HOURS`), а
  теперь — панелью.
- **Правка текстов точечными заменами по всему файлу** — в этом репозитории файлы CRLF,
  длинные русские строки в таких правках ломаются (битый символ → «0 вхождений»).
  Рабочий приём: правка по номерам строк скриптом + `git diff` на проверку.
