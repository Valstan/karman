## Failed approaches (этой нитки)

- **Считать, что перевод значений в `secrets` закрывает дамп журнала — неверно.** Маскировщик
  подменяет только **точное вхождение значения целиком**, а `journalctl` печатает хостнейм в
  короткой форме; короткая форма — префикс секрета, и маска её не трогает. Добросовестная
  починка «перенёс в secrets» оставила бы имя хоста в каждой строке с ощущением закрытой дыры.
  Лечится форматом (`-o cat`, `systemctl show` вместо `status`) и своей редакцией.
- **Искать 409-гейт в паспортном пути — его там нет.** Гейт живёт в `/api/secrets/provision`;
  паспорт туда не заходит и создаёт свою строку `secrets_token`. Мандат предполагал перевыпуск,
  которого в этой архитектуре не происходит.
- **Удалять старые `vars` до мержа правки** — открыло бы окно, в котором деплой из `main`
  уже не находит переменные. Порядок обязателен: secrets → мерж → зелёный прогон → удаление.
- **Проверять утечку грепом файлов репозитория** — бесполезно: значения в репозитории и не
  лежат (в том и был смысл D-038), а печатает их раннер. Смотреть надо `gh run view --log`.
- **`can_write=false` по умолчанию для новой личности** — в runbook'е пример был зашит на
  читателя; пишущему проекту это дало бы `403` на `POST`, что снаружи читается как
  «паспорт не работает».
- **Верить, что ssh-алиас = доступ.** `~/.ssh/config` ссылался на файл ключа, которого на
  этой машине нет вовсе; «алиас есть» ничего не доказывает, доказывает только живой коннект.

## Прод-инфра (для следующей сессии)

- **ssh:** алиасы `karman` и `GONBA`. На ЭТОЙ машине ключ прода заведён 2026-09-01 заново
  (старый остался на другой машине) — публичная часть добавлена в `authorized_keys` бокса.
  На новой машине первым делом проверять живым коннектом, а не наличием алиаса. Деструктив
  по прод-БД — только с подтверждением владельца в том же ходе (#025).
- **Свежая машина требует `npm ci`** — без него `npm run deadcode` врёт «knip не найден»
  и выглядит как сломанный инструмент, а не как отсутствующие зависимости.
- **Грабля psql по ssh:** `$DATABASE_URL` в env юзера НЕТ, переменные — в env-файле сервиса,
  путь берётся из юнита (`systemctl show karman -p EnvironmentFiles`). Рабочая форма:
  `ssh karman 'set -a; . <env-файл>; psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f -'`, SQL слать
  целиком через stdin. Колонки аудита: `at`, `action`, `detail`, `actor`; формат актора —
  префикс класса + идентификатор (`owner:1`, `passport:Valstan/trener`, `token:skm_…`).
- **Логи Actions публичны, `vars` в них не маскируются.** Recon-чувствительное — только в
  `secrets`; в `vars` осознанно оставлены два порта (маскировка «22» изуродовала бы лог).
  Любой новый шаг с дампом (`systemctl status`, `journalctl`) проверять по НАСТОЯЩЕМУ выводу
  с пустым грепом запрещённых токенов, а не по модели.
- **Внешние URL проверять С БОКСА** — с рабочей машины исходящий HTTPS идёт через прокси и
  таймаутит; `gh` при этом работает.
- **`main` защищён:** required check `gates`, PR обязателен, `enforce_admins`. Мержить после
  зелёного CI: `gh pr merge <N> --squash --delete-branch` (без `--admin`).
- **Миграции:** `deploy-prod.yml` блокирует авто-деплой на коммите с новой миграцией →
  применить psql'ом, затем `gh workflow run deploy-prod.yml --ref main`.
- **Деплой возит `scripts/`** на бокс вместе с артефактом. systemd-юниты — шаблоны, рендер
  через `scripts/render_unit.sh`; `cp` из репозитория положил бы сервис.
- **Бэкап vault:** cron 03:30, `scripts/backup_vault.sh`; список таблиц догоняет схему вручную.
