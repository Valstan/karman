## Текущая нитка

**Минимакс: пул обещал 101 аккаунт, а потребитель получал 0 (жалоба владельца 18.11, 21:00 МСК).**
Владелец: «все аккаунты снова оказались погашенными, хотя я знаю, что там ещё около 80 живые»,
и лог Сарафана: `свободных аккаунтов в пуле Кармана нет (no_free_accounts)`. Аудит Кармана в тот же
момент: «свободных аккаунтов нет (свободно 101)» — пул полон, а отказать нечем.

**Разбор (факты с прода, PR #365).**

1. **Отказ врал.** Цикл выдачи проверял 5 кандидатов и, сдавшись, всегда отдавал
   `no_free_accounts` — даже когда пул полон. Причина терялась.
2. **Первые пять кандидатов были невыдаваемыми.** Сторож, возвращая аккаунт в оборот, снимал
   отметку сессии (`used_at`) — и аккаунт вставал **в начало** списка как «никогда не
   активированный», то есть первым кандидатом на выдачу.
3. **Выдать их было нечем.** Правило «access уже отдан → тот же вход двоим не нужен» возвращало
   `null`. У 34 из 136 аккаунтов access был отдан и ещё жив (12 часов), refresh живой (HTTP 200),
   но код до него не доходил.

**Что сделано (PR #365, в проде).**

- **Возврат в оборот = новая выдача:** если access уже отдан, цепочка продлевается по refresh и
  новому потребителю уходит **новый** access. Тот же — двоим не отдаём.
- **Цикл выдачи: 25 кандидатов** и честная причина отказа: `no_free_accounts` (пул пуст) против
  `no_handable_accounts` (пул полон, но выдавать некому) + перечень пропущенных в аудите.
- **Сторож по мадату владельца (18.11, 21:40 МСК):** окно — выдачи **не моложе получаса**
  (`MIN_HANDOUT_AGE_MS`); **курсор** — время последней проверенной выдачи (идём по дереву выдачи
  вверх по времени); запись выдачи **не стирается** (освобождается только сессия) — иначе терялась
  и статистика «кому и сколько очков отдали», и сам след выдачи.
- **PR #367 (доводка):** курсор считается ДО раннего выхода (иначе вечером оставался null) и
  сверка после рестарта повторяется через 5 минут, а не через полчаса.

**Ответ владельцу на три вопроса (важно — это правда, а не интерпретация).**

- **Можем ли мы узнать, сколько очков на аккаунте?** Нет. Сырой ответ вендора
  (`signin/status`, проверено на 8 аккаунтах, обоих поясов) содержит только семь клеток с
  `day_no`, `status` (1/2/3/4), `points` (**номинал** клетки: 400 или 1000), `is_today` и
  `bonus_points` (**всегда 0**). Поля остатка нет нигде.
- **Что такое леджер?** Не предсказание и не живая правда о балансе. Это наша запись утреннего
  забора: «в 05:00 МСК клетку N забрали МЫ (или её уже забрал потребитель), номинал такой-то,
  вот кому и сколько очков отдали». Модель по датам из леджера вычищена.
- **Панель на сайте MiniMax показывает остаток?** Нет — она отдаёт ту же картину клеток
  (номиналы), остатка баланса в ответе нет.

- **Маркер обхода пишет приложение по факту завершения** (19.11): раньше его писал воркер

## Failed approaches (этой нитки)

- **Первый пересчёт расхождения модели с панелью был с ошибкой в SQL** (16.11: «клетка
  расходится у 73 из 109, класс у 48»): серия считалась как «сколько отметок за 7 дней»,
  а не как серия дней подряд. Правильный пересчёт — 42 из 112 и 3. Надёжный способ —
  сверять модель с внешней правдой ТОЙ ЖЕ формулой, какой считает код, иначе цифры
  выглядят правдоподобно и совсем не про то.
- **Состояние панели в памяти процесса** — не переживало рестарт и разъезжалось между
  чанками Turbopack: action и страница видели разное состояние одних и тех же
  аккаунтов. Теперь состояние в БД.
- **Проверка панели только для выбранного кандидата** — так аккаунт, у которого очки
  появились, в оборот не возвращался: его отсекала эвристика раньше, чем до панели
  доходила очередь. Теперь панель решает доступность заранее.
- **`activateAccount` возвращал `true` при проигранном CAS** — `return false` стоял
  внутри транзакции, наружу уходил `true`. Теперь результат транзакции возвращается
  наружу.
- **«24 часа от активации» как граница** — грубо: аккаунт, активированный в 23:50, ждал бы
  целые сутки, хотя сброс ночной. Заменено ночной границей (`DAILY_RESET_HOURS`), а
  теперь — панелью.
- **Правка текстов точечными заменами по всему файлу** — в этом репозитории файлы CRLF,
  длинные русские строки в таких правках ломаются (битый символ → «0 вхождений»).
  Рабочий приём: правка по номерам строк скриптом + `git diff` на проверку.

- **Правка текстов и замеров через CRLF и stdin** — не писать и не замерять файлы с кириллицей
  через PowerShell: `Get-Content -Raw | ssh ...` добавляет BOM (`﻿#!/usr/bin/env` → «No such
  file or directory») и портит кодировку. Рабочий приём: `Get-Content -Encoding UTF8 -Raw` +
  `ssh host "/bin/bash -s"` для bash-скриптов; для node — `scp` файла на бокс и запуск оттуда
  (BOM ломает `import`). Рабочий приём: править через `edit`/`.agents/patch.mjs` (нормализует
  CRLF→LF), а `git checkout -- <file>` на хосте блокируется гейтом.
- **«Догон» расписания по UTC-суткам** — «прошло ли уже 02:00 UTC сегодня» в 01:56 МСК (это
  22:56 предыдущих суток) отвечает «да». Граница, заданная в поясе владельца, считается **в его
  поясе** (живая находка 19.11; починено PR #369).
- **Проба пула, считающая только по строке леджера за сегодня, врёт в ночном окне** (между 00:00
  и 05:00 МСК строк за сутки ещё нет — забор впереди): пул по правилу приложения считает
  «нет открытой сессии», а не «есть строка леджера». Проба: `.agents/probe-night.sh`.
