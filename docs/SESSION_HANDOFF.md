## Failed approaches (этой нитки)

- **«Путь входа не привязывает» — утверждение о собственном коде, которое я не проверил.**
  Схема привязки строилась на нём, а ветка `linked_by_email` в `resolveOidcLogin` сама делает
  `INSERT` личности. Не поймай это разбор — кнопка «Отвязать» работала бы ровно до первого
  входа через ЕСА, молча возвращая снятую связь. Правило: утверждение про свой код в основании
  схемы — такой же признак, который надо прогнать, как условие `until:` у парка.
- **Отсрочка, обоснованная ценой, которой не существует.** Я решил не переименовывать
  сессионную cookie, потому что «это разлогинит всех». Разбор показал путь без разлогина
  (читать оба имени, писать новое) — то есть цена была не свойством задачи, а свойством
  первого пришедшего в голову решения. А отсрочка оставляла открытым захват учётки: сосед
  подбрасывает свою сессию, человек жмёт «Привязать» и отдаёт свою личность в чужой аккаунт.
- **Коммит в `main` вместо ветки.** После мержа #128 я остался на `main` и закоммитил туда
  следующий шаг; спасла защита ветки (push отбит). Коммит перенесён `git branch` без потерь.
  Привычка «после мержа сразу новая ветка» дешевле, чем разбор постфактум.

- **Диагноз, поставленный по одной стороне контура, отправил владельца чинить чужую
  систему.** Из «`auth_oidc_identity` пуста + почта в аудите пустая» я вывел «ЕСА не отдаёт
  подтверждённую почту» и написал владельцу идти настраивать ЕСА. Обе посылки были верны, а
  вывод — нет: я ни разу не спросил самого провайдера. Один `curl` по
  `.well-known/openid-configuration` показал `userinfo_endpoint` и `claims_supported` с
  `email`/`email_verified` — то есть отдавать он готов, а не ходили за этим мы. Правило:
  прежде чем объявить дефект чужим, прогнать признак **на его стороне**; у OIDC такой признак
  всегда есть и стоит одну команду.

- **Обещание, сформулированное как факт, стареет ровно как парк без прогона.** В письме
  утром 04.09 стояло «Ссылаюсь на G305 и G297 — в handoff и в `docs/passport-server.md`»,
  и обе стороны считали долг закрытым. `git grep G305` по своему же дереву нашёл два
  вхождения на весь репозиторий — оба в самом письме, где обещание и давалось. Правило:
  обещание соседу проверяется той же командой, что и признак парка, и в том же ходе.
- **Сторож, который узнаёт получателя только в момент отправки, молчит именно в аварии.**
  Первая редакция `health_watch.sh` звала разрешение `chat_id` из `send_telegram` — то есть
  кэш заполнился бы первым сигналом, а сигнал уходит тогда, когда что-то сломалось, возможно
  и сам Postgres. Поймано не рассуждением, а прогоном: после первого запуска
  `~/.karman-health/chat-id` оказался пуст. Разрешение перенесено в каждый прогон.
- **`WorkingDirectory=…/current` не означает «работает из текущего релиза».** Симлинк
  разрешается один раз при старте: процесс держит инод. Юнит, который деплой не
  перезапускает, переживает выкладку в старом каталоге, а чистка релизов этот каталог
  сносит — `readlink /proc/<pid>/cwd` показывает `(deleted)` при зелёном `systemctl status`.
  Проверка: сверить список юнитов, которые деплой рестартует, со списком тех, кто читает из
  релиз-каталога.
- **Агенту-разведчику верить только после сверки.** Проба доложила, что `/api/health`
  статический и БД не трогает (он ходит в неё `SELECT 1`) и что правки воркера с 30.08 не
  действуют (файл не менялся с 25.08). Обе ошибки — из чтения тела ответа и из даты старта
  процесса, без сверки с кодом и `git log`. Находка агента — гипотеза, а не факт.
- **Парк с проверяемым условием тоже протухает, если условие никто не прогоняет.** Пункт
  «MatricaRMZ обменивает времянку» закрылся 10.08 (строка `claim` в аудите) и прожил
  незамеченным до 04.09. Правило `/start`: `until:` — не текст, а запрос, который
  прогоняется при каждом всплытии соседних пунктов той же таблицы.
- **Предложение, которое занимает имя, — та же дыра с другого бока.** Первый черновик
  двустороннего grant'а оставлял уникальный индекс как был: чужая комната одним `POST`
  столбила бы имя у получателя без согласия. Индекс — только по принятым; гонка двух
  `accept` ловится нарушением уникальности, не предварительной выборкой.
- **`export` в `route.ts` помимо HTTP-методов** ломает типы маршрута Next — общий гейт

## Прод-инфра (для следующей сессии)

- **ssh:** алиасы `karman` и `GONBA`. Первый коннект в сессии может отвалиться по таймауту —
  повторить. Деструктив по прод-БД — только с подтверждением владельца в том же ходе (#025).
- **Порт приложения — 3002**, в юните, не в env-файле.
- **psql по ssh (D-046):** SQL пишется в файл, `scp` в `/tmp`, затем
  `ssh karman 'envf=$(systemctl show karman -p EnvironmentFiles --value | cut -d" " -f1); set -a; . "$envf"; psql "$DATABASE_URL" -f /tmp/<файл>'`.
  `\pset pager off` первой строкой; в `secrets_audit` колонка времени — `at`, не `created_at`.
- **`gh` периодически отдаёт TLS-таймаут** — повтор. `npm audit` в CI может вернуть
  `Bad Request` — `gh run rerun <id> --failed`.
- **Локальной базы на этой машине нет** — проверять сборкой, тестами, гейтом маршрута.
- **`main` защищён:** required check `gates`, PR обязателен, `enforce_admins`.
- **Миграции:** guard блокирует авто-деплой → psql → `gh workflow run deploy-prod.yml --ref main`.
  **Легаси-таблицы Django-эпохи (`documents_document`, `auth_user`, `credits_*`…) принадлежат
  роли `postgres`, новые — `karman_app`.** `ALTER TABLE` на легаси под `DATABASE_URL` даёт
  `must be owner of table`; применять такой файл как владельца:
  `db=${DATABASE_URL##*/}; sudo -n -u postgres psql -d "${db%%\?*}" -f /tmp/<файл>` (sudo без
  пароля на боксе есть). `scp` на бокс иногда рвётся `Connection closed` при живом ssh —
  файл доезжает через `ssh karman 'cat > /tmp/<файл>' < <файл>`.
- **Бэкап vault:** cron 03:30, `scripts/backup_vault.sh`; список таблиц догнал схему в #123.
