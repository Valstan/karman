**Пункты 10.10 закрыты 03.10 досрочно (решение владельца — «делаем»):**
- **Сессия стала отзываемой** — миграция `0019_session_epoch`: `auth_user.session_epoch`
  кладётся в токен при выдаче и сверяется в `getCurrentUser` на каждом запросе; растёт при

  отозвать до первого инкремента. Старые токены (без поля) не принимаются — осознанный разлогин
  всех устройств при применении миграции.
- **Step-up** (`lib/auth/step-up.ts`): сброс пароля, включение и выключение 2FA, блокировка
  учётки требуют либо второй фактор в текущей сессии, либо текущий пароль. Второй фактор не
  переспрашивается — сверяется claim `mfa` уже выданной сессии (спрашивать код в момент
  включения 2FA нельзя: включить её тогда можно было бы только у того, у кого она уже есть).

**Третья находка 10.10 закрыта 03.10 (S2, recovery-коды; решение владельца — «да, делай»,
выдавать заново):** миграция `0020_recovery_codes_kdf` (`auth_recovery_code.code_salt`,
NULL = строка старой редакции), `hashRecoveryCode` переведён на pbkdf2-sha256 600k с
индивидуальной солью на строку, легаси-ветка SHA-256 сохранена (без неё 10 живых кодов
перестали бы работать), формат кода 10 → 20 символов (~49,5 → ~100 бит), кнопка «выдать коды
заново» в панели 2FA за `requireAccountSecurity` + действующим TOTP-кодом, старое удаляется в
той же транзакции, аудит-событие `recovery_codes_regenerated`. Таблица `write-paths.md`
пополнена (68 действий), гейт на числа документа сработал и здесь.
- **Две ошибки, найденные при написании, а не при аудите.** Прежняя выборка была смещённой:
  `alphabet[b % 31]` при `256 % 31 ≠ 0` отдавал первые восемь букв чаще — энтропия была ниже
  49,5 бит. Моя первая «честная» замена `b & 31` — тоже ошибка: алфавит без `i/l/o/0/1`
  содержит **31** символ, а не 32, и часть байт давала индекс 31, то есть код выходил на символ
  короче (поймал тест на длину). Итог — отбрасывание байтов из хвоста (`>= 248 = 31×8`).
  Урок: «степень двойки» в коде выглядит доказательством корректности ровно до тех пор, пока
  кто-то не посчитал длину алфавита.
- **Что осталось за правкой:** легаси-ветка жива, пока в таблице лежат строки без соли. То есть
  вывод «дамп БД небезопасен по отношению к 2FA» перестаёт быть верным только после
  перевыпуска кодов кнопкой — не после миграции. Проверено на проде сразу после `0020`:
  `total=10, with_salt=0, unused=10` — то есть переходное состояние ровно то, которое задумано.
  **Следующий шаг за владельцем:** зайти в настройки 2FA и нажать «выдать коды заново» —
  после этого `with_salt` станет 10 и легаси-ветку можно убрать.

## Прод-инфра (для следующей сессии)

- **ssh:** алиасы `karman` и `GONBA`. Первый коннект может отвалиться — повторить.
  Деструктив по прод-БД — только с подтверждением владельца в том же ходе (#025).
- **Порт приложения — 3002**, в юните. Env-файл сервиса — см. `EnvironmentFile` юнита
  (`/etc/karman` root-only: правки только руками владельца, секреты агент не вписывает).
- **nginx на боксе — хозяин GONBA**; `default_server` держит vhost Гоньбы, наш vhost
  отвечает только по своему `server_name` (проверено 21.09).
- **psql по ssh (D-046):** SQL в файл → `ssh karman 'cat > /tmp/<файл>' < <файл>` →
  `ssh karman 'envf=$(systemctl show karman -p EnvironmentFiles --value | cut -d" " -f1); set -a; . "$envf"; psql "$DATABASE_URL" -f /tmp/<файл>'`.
  `\pset pager off` первой строкой. Временные файлы с персональными данными — удалять с бокса.
  **Windows-подводный камень (пойман 02.10):** PowerShell рвёт встроенные `"` на удалённую
  сторону и раскрывает `$VAR` локально — внешние кавычки одинарные, внутренних `"` в команде
  не оставлять, `$DATABASE_URL` должен остаться внутри одинарных; передачу делать файлом
  (`Get-Content -Raw | ssh … "tr -d '\r' > /tmp/…"`) — CRLF ломает bash/SQL.
  **Не-ASCII тем же путём не ездит вовсе** (поймано 02.10 на `detail` аудита):
  `Get-Content -Raw` в PowerShell 5.1 читает UTF-8 без BOM как ANSI и бьёт байты —
  кириллицу на бокс только ASCII-безопасно (`E'\uXXXX'`-литерал, base64+decode),
  с обязательной сверкой (`char_length`/`octet_length` против локального расчёта).
- **Загрузка документов пачкой:** генератор SQL + tar по slug → на бокс → psql в транзакции
  с `ingest_map` → `mv` в `$MEDIA_ROOT/documents/1/<id>/` → сверка путей `document_file` с

- **Легаси-таблицы Django-эпохи принадлежат `postgres`:** `ALTER` на них —
