# Шифрованный offsite-бэкап vault + media/ (vault Ф4)

Скрипт `scripts/backup_vault.sh` делает шифрованный бэкап секретов и сканов
документов и выгружает на Яндекс.Диск.

**Состояние на 2026-11-02 (проверено на проде, а не по документации):** правка выгрузки
смержена и **подтверждена боевым прогоном** (1 ч 52 мин, `ГОТОВО`, размер сошёлся) — до
этого 23 ночи подряд (09.10 — 31.10) архив на Диске НЕ появлялся, а сторож оставался
зелёным: он проверял свежесть лога, а лог писался каждую ночь. Разбор —
`docs/notes/backup-outage-2026-11-02.md`.
Cron владельца — 03:30 МСК, лог `~/backups/vault-backup.log`, шифрование — на подключ
`620308C1E7BFB120` ключа `99ECCA03BEDF6997D4F636DE9B610B3F2817F37A` (`KARMAN Vault Backup`).
**Закрытого ключа на прод-хосте нет** — так и задумано (pool #008).

**Частоты (решение владельца, 02.11 — «vault каждый день, media/ раз в неделю, не
проверяя»):** ежедневно уходит дамп vault (килобайты, секунды), снимок `media/`
(105 МБ, ~1 ч 45 мин по каналу ~17 КБ/с) — раз в неделю. Медиа меняются редко, а
выгрузка 105 МБ съедала ночное окно целиком.

Отсюда единственная незакрытая часть: **учебное восстановление ни разу не
прогоняли**, а прогнать его может только владелец — расшифровка требует его
закрытого ключа. См. «Учебное восстановление» ниже.

## Что и куда

- **Содержимое:** `pg_dump` vault-таблиц (`secrets_*`, `auth_totp`,
  `auth_recovery_code`, `auth_audit`) + (раз в неделю) `tar` каталога `media/` (сканы).
  Кредиты/документы/напоминания НЕ входят — только vault + media (охват выбран владельцем).
- **Шифрование:** весь архив шифруется gpg на **публичный ключ владельца** —
  расшифровать сможет только владелец своим приватным ключом.
- **Назначение:** Яндекс.Диск, папка `/KARMAN-backups` (WebDAV).
- **Ретенция:** два вида считаются ОТДЕЛЬНО — ежедневных vault хранится последние
  `BACKUP_KEEP` (14), недельных снимков media — последние `BACKUP_MEDIA_KEEP` (4).
  Считать их одним списком нельзя: ежедневные (килобайты) вытеснили бы недельные
  (105 МБ), и снимки перестали бы копиться.

## Два вида архивов

| архив | что внутри | как часто | размер | выгрузка |
|---|---|---|---|---|
| `karman-vault-YYYYMMDD-HHMMSS.tar.gpg` | `MANIFEST.txt` + `vault.sql` | каждую ночь | килобайты | секунды |
| `karman-media-YYYYMMDD-HHMMSS.tar.gpg` | `MANIFEST.txt` + `vault.sql` + `media.tar.gz` | раз в `BACKUP_MEDIA_INTERVAL_DAYS` (7) | ~105 МБ | ~1 ч 45 мин |

Решение «пора ли снимать media/» принимается по **подтверждённому** снимку
(`backup-media-ok-*`): снимков не было → пора; последний подтверждённый старше
интервала → пора; свежее → не пора. Календаря нет: если снимок не доехал, отметка не
обновилась и **следующей ночью попытка повторится сама**.

Недельный снимок идёт **после** ежедневного архива: если он упадёт (а он идёт
1 ч 45 мин), свежесть дампа за эту ночь уже обеспечена.

Восстановление собирается из двух файлов: **последний `karman-vault-*`** (свежий дамп)
и **последний `karman-media-*`** (свежие сканы). В `MANIFEST.txt` каждого архива есть
`media_included` (yes/no) и `media_last_confirmed` (дата последнего подтверждённого
снимка) — по манифесту видно, чего в этом архиве нет.

**Мастер-ключ (`SECRETS_MASTER_KEY`) в бэкап НЕ входит** (корень доверия, pool #008).
Значения секретов в дампе уже зашифрованы им; gpg — второй слой. Дамп без
мастер-ключа секреты не раскрывает — мастер-ключ владелец хранит отдельно.

## Настройка (владелец — один раз)

### 1. Пароль приложения Яндекса (для WebDAV)

Основной пароль при 2FA не подходит — нужен **пароль приложения**:
Яндекс ID → Безопасность → Пароли приложений → создать для «WebDAV».
Затем дописать в env-файл сервиса на прод-хосте (путь — `EnvironmentFile` в systemd-юните;
значения — не в git):

```
YANDEX_WEBDAV_USER=<логин-яндекса>
YANDEX_WEBDAV_PASSWORD=<пароль-приложения>
```

### 2. Публичный gpg-ключ владельца (для шифрования)

Экспортировать свой публичный ключ и импортировать на прод-хосте:

```bash
# на своей машине:
gpg --export --armor <ваш-ключ> > karman-owner.pub.asc
# скопировать на прод-хост и импортировать под deploy-пользователем:
scp karman-owner.pub.asc karman:~/
ssh karman 'gpg --import ~/karman-owner.pub.asc && rm ~/karman-owner.pub.asc'
```

Взять fingerprint (`gpg --list-keys`) и дописать в env:

```
BACKUP_GPG_RECIPIENT=<fingerprint-или-email-ключа>
```

> Если своего gpg-ключа нет — создать: `gpg --full-generate-key` (RSA 4096),
> приватный держать в надёжном месте (без него бэкап не восстановить).

## Что скрипт доказывает, а что нет

С 2026-08-10 «ГОТОВО» несёт свидетельства, а не только факт завершения:

- `tar media/ (файлов: N)` — сколько файлов реально упаковано. **`N = 0` при живых
  документах** означает, что приложение пишет сканы не туда, куда смотрит бэкап
  (сверить `MEDIA_ROOT` в systemd-юните с `BACKUP_MEDIA_ROOT`); в лог уходит
  отдельная строка `ВНИМАНИЕ`.
- `выгрузка подтверждена размером (N Б), код curl=X` — размер файла **на Диске**
  сверен с локальным через HEAD. Успешный `PUT` сам по себе означает «сервер
  принял запрос», а не «на Диске лежит целый файл»: обрыв на середине даёт
  бэкап, который выглядит существующим ровно до дня восстановления.
  **Решает факт, а не код клиента:** 01.11 и 02.11 curl ругался (52/56), а файл
  доезжал целиком — сервер дописывал его ещё 24 минуты после того, как клиент
  отвалился. Поэтому код curl в сообщении есть, а решение принимает размер.
- `MANIFEST.txt` внутри архива несёт `media_files_on_disk`, `media_included` (yes/no),
  `media_bytes`, `media_last_confirmed` (дата последнего подтверждённого снимка) и
  `vault_sql_bytes` — при восстановлении видно, совпало ли распакованное с
  упакованным, и чего в этом архиве нет.
- `снимок media/ ПОРА …` / `снимок media/ не пора …` — какое решение принято о
  еженедельном снимке и почему (последний подтверждённый снимок и интервал).

Чего скрипт **не** доказывает: что архив расшифровывается. Это доказывает только
учебное восстановление.

## Что происходит при обрыве выгрузки

Поведение задаёт `scripts/backup_upload.sh` (логика вынесена, чтобы её можно
было прогнать без бокса — гейт `lib/security/backup-upload.test.ts`):

1. `PUT` упал или вернул ошибку → **не роняем скрипт**, идём к сверке размера.
2. Размер на Диске совпал → **успех**, повторной выгрузки нет (105 МБ ≈ 1 ч 45 мин
   — повтор не бесплатный).
3. Размер не совпал, но ресурс на Диске есть → сервер ещё дописывает: ждём
   (по умолчанию до 30 минут, шаг 60 с) и перепроверяем.
4. Всё ещё не совпал → **одна** повторная попытка выгрузки.
5. И она не удалась → **локальная копия** архива остаётся в `BACKUP_KEEP_DIR`
   (по умолчанию `~/backups/pending`), скрипт завершается с ошибкой. Раньше
   архив удалялся вместе с временным каталогом, и обрыв уничтожал единственный
   экземпляр файла.

## Отметки: как сторож узнаёт, что бэкап БЫЛ

Скрипт бэкапа пишет в `$HOME/.karman-health` (каталог — `BACKUP_OK_DIR`):

- `backup-run-YYYYMMDD` — запуск начался; файл обновляется каждые 60 секунд
  («пульс»), пока идёт выгрузка. Без пульса длинный PUT выглядел бы как
  мёртвый запуск.
- `backup-ok-YYYYMMDD` — ежедневный бандл vault подтверждён размером. Дата — по
  **началу** запуска: ночь 30.10 → 01.11 — это ночь 30.10.
- `backup-media-run-YYYYMMDD` — попытка снять недельный снимок `media/` началась
  (пишется **до** выгрузки: видно, что снимок пошёл, но не доехал).
- `backup-media-ok-YYYYMMDD` — снимок `media/` подтверждён размером. По этой отметке
  принимается решение «пора ли снимать на следующей ночи».

Сторож (`scripts/health_watch.sh`, раз в 10 минут) читает все четыре:

- пульс свежий (меньше 45 минут) → запуск идёт, тревогу не поднимаем;
- пульс протух, а `backup-ok` нет → **«бэкап vault НЕ подтверждён»** — ровно тот
  сигнал, которого не было 23 ночи подряд;
- `backup-media-run` есть, а `backup-media-ok` за ту же дату нет → **«снимок
  media/ НЕ подтверждён»** (спасение: ежедневный дамп за эту ночь уже есть);
- последний `backup-media-ok` старше 9 дней → **«снимок media/ старый»** (мягкая
  тревога: снимок недельный).

Признак для ручной проверки (минута):

```bash
ls -t ~/.karman-health/backup-run-* ~/.karman-health/backup-ok-* \
      ~/.karman-health/backup-media-run-* ~/.karman-health/backup-media-ok-* 2>/dev/null | head -8
```

## Ручной запуск (проверка)

```bash
# ENV_FILE — env-файл сервиса (путь: `systemctl show karman -p EnvironmentFile`).
ssh karman 'ENV_FILE=<путь-из-юнита>; set -a; . "$ENV_FILE"; set +a; cd ~/karman && bash scripts/backup_vault.sh'
```

Тот же прогон доступен без ssh — одной кнопкой в GitHub Actions:
`gh workflow run run-backup.yml -f "reason=проверка"` (воркфлоу `.github/workflows/run-backup.yml`,
команда в нём зашита; бокс с машины агента недоступен — ключ деплоя есть только в
секретах Actions).

Успех: строка `backup_vault: ГОТОВО — karman-vault-….tar.gpg` (и, если пора,
`+ karman-media-….tar.gpg`). Проверить, что файлы появились на Яндекс.Диске в
`/KARMAN-backups`.

## Расписание (после успешной ручной проверки)

Ночной запуск через user-crontab (root не нужен):

```bash
# APP_BASE — корень рабочей копии на прод-хосте, ENV_FILE — env-файл сервиса
# (путь: `systemctl show karman -p EnvironmentFile`). Литералы в git не держим.
# `\$HOME` намеренно не раскрывается здесь — его подставит sh при запуске из cron.
ssh karman 'APP_BASE=<корень-рабочей-копии>; ENV_FILE=<путь-из-юнита>; crontab -l 2>/dev/null; echo "30 3 * * * set -a; . $ENV_FILE; set +a; bash $APP_BASE/scripts/backup_vault.sh >> \$HOME/backups/vault-backup.log 2>&1" | crontab -'
```

(03:30 ежедневно; лог — `~/backups/vault-backup.log`.)

## Учебное восстановление (владелец, раз в квартал)

Бэкап, который ни разу не разворачивали, — это надежда, а не бэкап. Прогон нужен
целиком на **своей машине**, прод не трогается.

```bash
# 1. Скачать ДВА архива (пароль приложения Яндекса — тот же, что на боксе):
#    последний karman-vault-* (свежий дамп) и последний karman-media-* (свежие сканы)
curl -fsS --user "<логин>:<пароль-приложения>" -o last-vault.tar.gpg https://webdav.yandex.ru/KARMAN-backups/karman-vault-<STAMP>.tar.gpg
curl -fsS --user "<логин>:<пароль-приложения>" -o last-media.tar.gpg https://webdav.yandex.ru/KARMAN-backups/karman-media-<STAMP>.tar.gpg

# 2. Расшифровать СВОИМ закрытым ключом — это и есть проверяемое звено
gpg --decrypt last-vault.tar.gpg > vault-bundle.tar
gpg --decrypt last-media.tar.gpg > media-bundle.tar

# 3. Распаковать и сверить с манифестом
#    Распаковывать ВНЕ рабочей копии git: vault.sql — это выгрузка vault-таблиц,
#    и в индексе репозитория ему не место (S4, аудит #057). Каталог — отдельный,
#    не внутри репозитория.
mkdir -p ~/karman-restore && cd ~/karman-restore
tar -xf vault-bundle.tar                  # → MANIFEST.txt, vault.sql
tar -xf media-bundle.tar                  # → MANIFEST.txt, vault.sql, media.tar.gz
cat MANIFEST.txt                          # ожидаемые media_* / vault_sql_bytes, media_included
tar -tzf media.tar.gz | grep -c .         # должно совпасть с media_files_on_disk (+1 на сам каталог)
grep -c "^INSERT\|^COPY" vault.sql     # дамп не пустой

# 4. Проверить, что секреты расшифровываются ТЕМ ЖЕ мастер-ключом:
#    поднять vault.sql в ЛОКАЛЬНУЮ базу и прочитать один ключ с SECRETS_MASTER_KEY.
#    Без мастер-ключа архив бесполезен — это отдельное звено, и оно тоже учебное.
```

**Записывать дату успешного прогона** — в `docs/PENDING_FOLLOWUPS.md`, пункт про
учебное восстановление (`last-run:`). Без даты «мы это проверяли» превращается в
воспоминание.

> ⚠️ **Единственная точка отказа — не прод-хост, а хранение закрытого ключа.** На прод-хосте
> его нет (проверено). Если единственная копия закрытого gpg-ключа лежит на одной машине
> и она умрёт, **все** архивы станут нечитаемыми — данные при этом целы, а бэкап нет.
> То же про `SECRETS_MASTER_KEY`: без него дамп отдаёт шифротекст.

## Восстановление

```bash
# скачать с Яндекс.Диска нужные архивы (последний karman-vault-* и последний
# karman-media-*), затем:
# РАСПАКОВЫВАТЬ ВНЕ рабочей копии git — vault.sql не должен оказаться в индексе
# репозитория (S4, аудит #057: цена такого коммита — необратимая утечка ПДн).
mkdir -p ~/karman-restore && cd ~/karman-restore
gpg --decrypt karman-vault-YYYYMMDD-HHMMSS.tar.gpg > vault-bundle.tar   # приватным ключом владельца
gpg --decrypt karman-media-YYYYMMDD-HHMMSS.tar.gpg > media-bundle.tar
tar -xf vault-bundle.tar              # → MANIFEST.txt, vault.sql
tar -xf media-bundle.tar              # → MANIFEST.txt, vault.sql, media.tar.gz
# секреты: восстановить таблицы в БД (осторожно на живом проде — #025):
psql "$DATABASE_URL" -f vault.sql
# сканы (из недельного снимка media):
tar -xzf media.tar.gz -C <куда-нужно>
```

Расшифровка значений секретов после восстановления требует того же
`SECRETS_MASTER_KEY`, что был на момент бэкапа (у владельца).
